## 2. 结论摘要

建议下一轮主题是**让恢复流程真正回到可信的可操作状态**，而不是继续增加入口。
本轮筛出 10 项：1 High、8 Medium、1 Low；9 项缺陷和 1 项体验增强机会。
其中 5 项是上一批新入口／恢复机制的交互缺口，5 项是邻近路径的继承问题。
第一优先是避免项目读取短暂失败清空已打开的新建草稿。
第二优先是让批量核对结果同步到列表和选择状态，并允许已核对项单独恢复操作。
第三优先是给撤销、排序和在途等待补齐生命周期与时限边界。

## 4. 具体发现

### 4.1 表单与输入

#### FORM-03 · 项目元数据短暂失败会关闭新建弹窗，恢复后重置草稿

| 字段 | 内容 |
| --- | --- |
| 维度 | Input & forms；关联 State coverage |
| 严重度／性质 | **High**／缺陷，上一批项目空状态入口引入的组合问题 |
| 置信度 | **Observed (code)；丢草稿交互结果 Inferred，未运行复现** |
| 位置 | `apps/web/features/projects/project-conversation-list.tsx:114–142,375–380`；`apps/web/features/conversations/new-conversation-dialog.tsx:35–49` |
| 工作量 | M |

**证据。** 项目页把 `!projectsQuery.isError` 纳入 `canAddToProject`，再用
`open={newConversationOpen && canAddToProject}` 控制整个弹窗。新建组件在
`open` 从 false 变 true 时重置标题、项目和两段输入。用户主动关闭时的脏草稿
确认，不能拦截父组件直接把 `open` 置 false。

**用户后果。** 用户已经输入内容时，后台项目信息读取最终报错会隐藏弹窗；
读取恢复又自动打开同一入口并重置输入。暂时不能确认项目状态，不应被解释为
用户放弃了这份草稿。这里不要求账号失效后继续展示旧账号内容。

**建议。** 用显式编辑会话控制弹窗及初始化；将“可以开始新建”和“已打开草稿
能否提交”分开。暂时读失败保留输入，显示“项目信息暂不可用，草稿已保留”，
提供只读重试并阻止不安全提交。项目删除／归档应明确解释目标失效；账号退休
继续执行现有隐私隔离，不能借保草稿绕过权限边界。

**待验收。** 在空项目打开表单并填写合成文本，制造项目信息刷新 503 后恢复；
弹窗不意外消失，输入逐字保留，没有自动创建。再分别覆盖目标归档、删除和
账号变化。已有 `scripts/ux/project-recovery.test.mjs:445–458` 的空入口检查
不等价于这个“弹窗已经打开”的连续状态场景。

#### FORM-04 · 手动创建仍不能安全重放已提交但丢失响应的请求

| 字段 | 内容 |
| --- | --- |
| 维度 | Input & forms；关联 Error prevention & recovery |
| 严重度／性质 | **Medium**／继承缺陷，不是上一批拆分回执的新回归 |
| 置信度 | **Observed (code)；重复创建的网络时序结果 Inferred** |
| 位置 | `apps/web/features/conversations/new-conversation-dialog.tsx:51–72,140–161`；`apps/web/lib/api.ts:235–236`；`apps/api/app/api/routes/conversations.py:86–111` |
| 工作量 | L |

**证据。** `submitting` 只防同时点击；请求结束后重新开放提交。
API 的创建端点直接创建并 commit，没有该操作的幂等身份／回执。
未知错误文案要求用户自行去列表检查，而再次提交仍是普通 POST。

**用户后果。** 服务器已经提交但浏览器未收到响应时，用户无法凭同名列表项
可靠确认是否是这一笔创建；重试可能多出一份相同对话。源内容不会因此被删除，
因此不把它升级为不可逆数据破坏。

**建议。** 借鉴现有拆分／任务的安全身份模式，为手动创建定义账号隔离的同请求
回执：同键同载荷返回原结果，同键不同载荷明确冲突，创建与回执一起提交。
前端未知状态冻结原输入和身份，提供“安全重试本次创建”；明确完成或明确放弃
该未知操作后的新意图，才允许另起请求。不能以标题匹配代替身份。
需先设计兼容无键旧调用、删除后回放和保留策略，不在纯前端补一个防抖就宣称解决。

**待验收。** 必须构造真实 commit 后丢响应、并发同键、载荷冲突、账号隔离；
断言只产生一个结果，原输入不变，旧客户端兼容。若涉及新 migration，
同步 schema／model／测试和部署边界，保持单一 head；本轮不新增或执行迁移。

### 4.2 错误预防与恢复

#### ERR-03 · 核对面板读到了新状态，列表和选择仍可能停在旧状态

| 字段 | 内容 |
| --- | --- |
| 维度 | Error prevention & recovery；关联 Data display |
| 严重度／性质 | **Medium**／上一批新增恢复机制的闭环缺口 |
| 置信度 | **Observed (code)；旧列表再次准入操作的交互结果 Inferred** |
| 位置 | `apps/web/features/conversations/use-batch-result-check.tsx:61–79,88–108`；`apps/web/features/conversations/conversation-list.tsx:331–338,486–497,645–670`；`apps/web/features/projects/project-conversation-list.tsx:179–186,442–453` |
| 工作量 | M |

**证据。** 核对 hook 只把 GET 结果写入自己的 `checked`，没有缓存发布或宿主
协调回调。“已核对，按当前状态继续”仅修改 `released` 并移除 blocked IDs。
宿主保留未确认项的选择，操作参数仍来自列表查询。归档完成但响应丢失、随后列表
刷新又失败时，旧活动行会保留；详情核对成功并不使该行自动退出旧列表。

**用户后果。** 同屏可以一边显示“已归档”，另一边仍把旧行当活动对话提供归档、
移动或合并入口。“按当前状态继续”表达了比实际状态同步更强的承诺。
不是核对按钮会自动重写，而是用户下一次明确点击可能基于未校准的旧上下文。

**建议。** 将核对结果交给宿主做有范围的状态协调：取消旧读取的覆盖机会，
发布已知字段，剔除不再属于当前活动／归档范围的选择，并重读受影响范围。
项目成员关系不能只凭详情里的单一 `project_id` 摘要重建，应使用权威项目范围
或现有 placement 合同核实。无法校准的行继续禁用，已校准的行再由用户明确放行。
可复用 `conversation-placement.tsx` 已有的取消旧读／发布模式，不要新建缓存体系。
核对依然不是原请求回执，不能因此扩大 Undo。

**待验收。** 保持列表 GET 失败，让详情 GET 成功返回已归档／已移动状态，
再点击继续；旧行不能作为仍有效的旧范围项再次提交。覆盖迟到旧 GET、分页对象、
旧数组缓存及多项目关系。已有浏览器场景
`apps/web/e2e/ux-recovery-followup.spec.ts:2262–2313` 断言核对不新增写入，
但没有断言继续后的列表、选区和下一步操作已经协调。

#### ERR-04 · 单项读取失败会连带阻塞全部已核对项

| 字段 | 内容 |
| --- | --- |
| 维度 | Error prevention & recovery；关联 State coverage |
| 严重度／性质 | **Medium**／上一批新增恢复机制的粒度缺口 |
| 置信度 | **Observed (code)；真实混合失败下的操作成本 Inferred** |
| 位置 | `apps/web/features/conversations/use-batch-result-check.tsx:9–17,72–79,88–106` |
| 工作量 | M |

**证据。** 状态只保留 `failedCount`，不保留失败项身份及原因；每次核对清空
已读结果并重读全部 ID。只有 `checked.length === ids.length && !failedCount`
才显示继续按钮；放行前 `blockedIds` 是整组 ID。

**用户后果。** 多项里只有一项被删除、失去访问权或持续读取失败，也会让其他
已核对项无法在当前恢复面板中解锁。取消选择并重新选择这些 ID 仍会命中整组拦截；
不是全站不可用，但用户容易被迫离开页面，丢掉本次核对上下文。

**建议。** 按项保存“当前状态已读／暂时不可读／不可访问”的结果；只重试未解决项。
结合 ERR-03，允许用户明确“继续处理已核对的 N 项”，其余项继续隔离并显示原因。
不可访问或 404 不能推断原操作成功，也不能泄漏无权查看的标题／项目。
账号失效仍整体退休，不能将 401 当普通单项故障绕过。

**待验收。** 合成三项分别正常、503、404；正常项经协调和明确确认后可操作，
其余不放行，不生成 Undo，也不重复读取已完成项（除非用户主动要求更新）。
现有 `scripts/ux/batch-action-recovery.test.mjs:149–160` 只检验单项失败不放行，
需要补混合结果而不是删除原安全断言。

#### ERR-05 · Undo 的异步队列没有跟随操作所属页面／账号退休

| 字段 | 内容 |
| --- | --- |
| 维度 | Error prevention & recovery |
| 严重度／性质 | **Medium**／继承缺陷；上一批仅调整该组件的失败分类，未新引入此问题 |
| 置信度 | **Observed (code)；卸载后继续派发的时序结果 Inferred** |
| 位置 | `apps/web/features/conversations/conversation-undo.tsx:3,40–76`；`apps/web/lib/batch-selection.ts:46–72`；对照 `apps/web/features/conversations/conversation-list.tsx:81–95,341–362` |
| 工作量 | M |

**证据。** Undo 的写入与核对均调用没有 signal 的 `runBatchSelection`；
组件没有卸载清理或认证代际校验。父组件清除 Undo 界面，不会停止已启动的队列；
队列在已发请求返回后仍可领取下一项，最后还会执行 `onDone`／`onChanged`。
首次批量操作已经具备的生命周期保护没有传递到这条逆向路径。

**用户后果。** 用户已经切走列表或退出账号，旧撤销动作仍可能派发尚未开始的请求，
或用旧完成回调影响新的页面状态。这里不声称能跨越服务端所有权检查；
问题是操作寿命不再由当前上下文控制。

**建议。** 为 Undo 实例绑定 action 身份、挂载状态和认证代际；退休时只停止后续
派发，逐项派发及发布结果前检查身份。已发送请求仍保守结算，不将 UI 关闭当作
服务器回滚；旧实例不清理新 Undo，也不向新账号／新范围发布迟到结果。

**待验收。** 在 12 项队列中持有前 4 个请求，分别切范围、卸载、换账号；
释放前 4 项后，其余 8 项不派发，旧回调不影响新实例。保留已确认项不重放、
未知结果先 GET、只重试已核对未应用项等已有行为。

#### ERR-06 · 拆分安全重试被不必要的完整时间线读取挡住

| 字段 | 内容 |
| --- | --- |
| 维度 | Error prevention & recovery；关联 Perceived performance |
| 严重度／性质 | **Medium**／上一批新增回执恢复的交互缺口 |
| 置信度 | **Observed (code)；慢读下的恢复阻塞 Inferred** |
| 位置 | `apps/web/features/editing/conversation-split-workspace.tsx:99–132,211–226,320,336–344`；`apps/web/lib/api.ts:533–544` |
| 工作量 | M |

**证据。** 关闭重开时能恢复原请求、预览和幂等键，但仍启动完整索引分页读取；
安全重试按钮及执行函数都因 `loading` 被禁用。该读取没有请求 signal 或客户端
时限。原计划重放实际使用已冻结的 `attempt.request`，不依赖刚重读的时间线。

**用户后果。** 已有安全恢复身份，却必须等待与回执无关的完整对话加载。
只要其中一页迟迟不返回，即使拆分回执接口可用，用户也不能立即重试同一请求。
不是所有读取错误都会永久阻断：读取明确失败后 `loading` 会结束。

**建议。** 将“读取索引以形成新计划”和“重放冻结计划”分开。待确认计划直接
展示原摘要并允许同身份恢复；后端仍验证来源权限和载荷，不绕过授权。
普通新计划继续等待完整索引和范围校验，关闭／退休后停止无用的索引请求。

**待验收。** 已提交丢响应后关闭重开，持有索引下一页但允许回执接口返回；
用户仍可恢复原结果且没有额外副本。新计划不得趁索引未完成而创建；
账号变化、来源失权和旧请求迟到不污染当前工作区。

### 4.3 系统状态与反馈

#### FBK-03 · “停止后续操作”不能解决在途请求缺少客户端时限

| 字段 | 内容 |
| --- | --- |
| 维度 | System status & feedback；关联 Error prevention & recovery |
| 严重度／性质 | **Medium**／继承缺陷，新进度界面使这一边界更明显 |
| 置信度 | **Observed (code)；实际卡顿时长未测量** |
| 位置 | `apps/web/lib/api.ts:454–459,910–913,935–942,1720–1754`；`apps/web/lib/batch-selection.ts:46–73`；`apps/web/features/conversations/conversation-list.tsx:341–362` |
| 工作量 | M |

**证据。** 归档、恢复、移项目等请求没有客户端 deadline；`fetchJson` 直接等待
fetch 和响应体。批量函数等待全部 worker 结束，signal 只控制后续派发。
“停止”不会令当前未返回的请求结束，所以批次结果和部分恢复入口仍需等待。
本审查不把这描述成“网络永远不会超时”，代理／浏览器可能有自己的限制。

**用户后果。** 用户已经停止剩余工作，仍无法知道何时能进入核对或继续操作。
界面显示停止，并不等于这批操作已经结算。

**建议。** 分离两个概念：停止 signal 只控制派发；单请求有覆盖响应体阶段的
独立时限。时限到达进入“结果未确认”，保留核对入口，绝不能标成服务器已取消、
明确失败或自动重试。预算依据接口规模和 CI 场景确定，不为通过测试任意延长。
避免只做 `Promise.race` 而无限遗留请求及迟到回调。

**待验收。** 持有响应头、持有响应体、真实 commit 后超时分别覆盖；停止后不发
新请求，已确认项不重放，超时项只进入核对，五类计数守恒，界面最终能退出忙碌态。

#### FBK-04 · 核对面板缺少“这批原本想做什么”的稳定摘要

| 字段 | 内容 |
| --- | --- |
| 维度 | System status & feedback |
| 严重度／性质 | **Low**／体验增强机会，不是已有安全约束失效 |
| 置信度 | **Observed (code)；理解成本的真实频率 Inferred** |
| 位置 | `apps/web/features/conversations/use-batch-result-check.tsx:9–17,48–58,91–100`；`apps/web/features/conversations/conversation-list.tsx:331–338`；`apps/web/components/bulk-move-review.tsx:21–33` |
| 工作量 | M |

**证据。** 核对状态保留 ID、当前详情和数量，不保留原动作、目标及批次身份；
后续未知结果会与早先 ID 合并。移动目标属于确认控件自己的临时状态，不是
与核对记录绑定的原意图摘要。

**用户后果。** 中断后回来，用户看到“当前在项目 C”，但不易判断原本确认的是
移动到 B、从 A 移除，还是归档。多个批次混在一起时尤其依赖记忆。

**建议。** 在现有内存范围内保留有界的动作摘要：动作、确认数量、目标名称与
稳定身份、当前检查时间。按批次呈现“原计划／当前状态”，允许只重试读取；
明确当前状态不证明原请求成功。不要把单一项目摘要冒充全部项目成员关系，
也不必为这项增强新建持久任务系统或保存对话正文。

**待验收。** 连续两笔不同目标的未知操作仍可分别辨认；退出选择模式不抹掉
仍由当前列表拥有的摘要；账号退休清理旧内容，任何摘要都不自动触发写入。

### 4.4 数据展示与排序

#### DATA-05 · 全局列表缺少拖拽开始时的数据版本校验

| 字段 | 内容 |
| --- | --- |
| 维度 | Data display |
| 严重度／性质 | **Medium**／继承缺陷，项目列表的新保护尚未覆盖全局列表 |
| 置信度 | **Observed (code)；浏览器拖拽／刷新竞态 Inferred** |
| 位置 | `apps/web/features/conversations/conversation-list.tsx:222–257`；对照 `apps/web/features/projects/project-conversation-list.tsx:220–260` |
| 工作量 | M |

**证据。** 全局列表只在放下时检查当前 fetching／error／完整性等条件；
开始时记录拖拽 ID 和尺寸，没有冻结查询版本或操作代际。项目页已经比较
project、mode、direction、generation 和 `dataUpdatedAt`。

**用户后果。** 拖拽期间后台刷新完成后，放下时 `isFetching` 又是 false，
旧拖拽意图可能对新列表顺序发起写入。用户拖动时看到的相邻关系与实际提交范围
不再是同一份数据；该时序尚待真实 DnD 验证。

**建议。** 沿用项目页的范围／读取版本保护，开始和结束都校验；
范围、方向、权限或读取代际变化即退休原拖拽。旧失败不得在新范围显示错误。
不要改掉既有升降序 canonical rank 和全局置顶时间优先级。

**待验收。** 开始拖拽后完成一次改变顺序的后台刷新，再放下应零写入；
范围／方向切换同样覆盖。没有变化时仍可正常保存并重读得到相同可见顺序。

#### DATA-06 · 项目自定义拖拽允许跨置顶边界，但服务端始终先排置顶

| 字段 | 内容 |
| --- | --- |
| 维度 | Data display；关联 System status & feedback |
| 严重度／性质 | **Medium**／继承缺陷 |
| 置信度 | **Observed (code)；视觉回跳表现 Inferred** |
| 位置 | `apps/web/features/projects/project-conversation-list.tsx:228–234,517–562`；`apps/api/app/services/projects/project_service.py:505–513`；`apps/api/app/api/routes/projects.py:201–211` |
| 工作量 | M |

**证据。** 项目页直接对整组 `arrayMove` 后保存 rank，没有判断源和目标的
`project_relation.is_pinned`。API 写入 rank，但 custom 读取先按置顶状态分组，
然后才按 rank。拖拽并没有修改置顶状态。

**用户后果。** 用户把普通行拖到置顶行前面，保存后仍会回到普通组；
部分操作还会改变组内次序，却永远无法得到拖拽所表达的跨组顺序。
界面没有像全局列表那样解释这个边界。

**建议。** 将跨组目标判定为不可提交，并提示“置顶对话始终在前；
可先取消置顶，再调整顺序”。保留组内拖动和非拖拽操作。
项目 custom 只由置顶布尔值划组，不能误套全局列表的 `pinned_at` 分组条件。

**待验收。** 跨组拖放不写入并有可理解提示；置顶组内部、普通组内部都能保存。
检查不同置顶时间仍可在项目置顶组内重排，避免过度限制。
