## 实测问题与修改

使用同一 Chrome、同一合成表格，在真实 SourceEditorWorkspace / EditMessageForm /
CodeMirror 中打开工具，逐次输入五个字符，观察 input 事件至 Markdown 更新后下一
帧的耗时。不是纯函数微基准，不访问真实账户或导入数据。

初始实现每次改单元格，除序列化整个表格更新 Markdown 外，还在 render 中重复
序列化，并调用完整 replacement 转换：重新识别没有变化的原文范围、解析原表格
及草稿、再序列化结果。预览布局验证更新状态时，实际 Markdown 树也会重复解析。

本轮修改：

- 接受的表格模型与其规范 Markdown 一起更新，不再为同一按键序列化两次。
- 输入时仍完整检查规范草稿，但不重新解析已经冻结的原文。点击应用后，父级
  仍检查当前 CodeMirror 修订/文本，并执行完整 `applyMarkdownTableAction`，
  不绕过范围、UTF-8 大小或原文变化保护。
- `renderCell` 身份稳定；共享编辑预览使用 `memo`，布局验证或状态反馈没有改变
  文本/单元格数据时，不再重复执行 Markdown 解析链。单元格编辑和无效状态仍
  正确更新，不缓存过期内容。
- 没有竖线/转义竖线的单元格直接复用字符串，不逐字符重新拼接。
- 缓存只属于当前打开的工具，没有进程级缓存、新依赖或服务器变更。

## 有界性能观察

Windows、本机未降速的 headless Chrome **155.0.8059.82**；每组五个字符。
“单元格数”包含表头和分隔行，DOM 数只计算实际挂载的 `th/td`。

| 合成输入 | UTF-8 字节 | 逻辑单元格 | 挂载单元格 | 输入耗时中位数：前 → 后 |
| --- | ---: | ---: | ---: | ---: |
| 6 列、20 数据行 | 1,009 | 132 | 126 | 15.2 → 11.8ms |
| 12 列、80 数据行 | 8,017 | 984 | 372 | 36.5 → 26.0ms |
| 10 列、4,000 数据行 | 397,013 | 40,020 | 310 | 132.5 → 92.9ms |
| 200 列、248 数据行 | 499,309 | 50,000 | 1,200 | 216.2 → 126.2ms |

最新复跑大表/宽表中位数分别减少约 **29.9% / 41.6%**。更早一次优化后观测为
90.7 / 121.8ms，原始数据一并保留；两次之间只改测试结果时效保护，产品代码
不变，差异不当成新的产品优化。这是小样本本机观察，
不是跨设备保证、p95、INP 验收或 CI 性能阈值。最大两组仍存在长任务，不宣称
所有表格达到每秒 60 帧；没有用缩小完整应用范围来换取数字。

脚本也保留显式 GC 后的 JS heap 观察：最大宽表五次输入后约 **23.91 → 19.31
MiB**，大窄表约 **19.19 → 15.08 MiB**。这不是 RSS、峰值分配量或泄漏证明；
只观察五次输入，不能据此宣布服务端 OOM、长时间浏览器内存或低内存问题解决。

## 回归

- 原 20 场景保持通过，新增两项实际工作区回归：
  - 单元格未闭合语法保留输入和焦点、禁用应用；修复后可继续交替编辑 Markdown /
    网格，最后应用的是最新规范文本，周围正文不变。
  - 单元格输入导致超出 1 MiB 时，整次输入被拒绝，保留上一有效单元格与 Markdown；
    不截断，不发布部分变更。
