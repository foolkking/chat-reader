## 修复与复核顺序

1. 先修可发布链路：独立中心、真实来源适配与稳定选择/计划/回执，继续复用单对话内核，不修改已有来源安全边界。
2. 并行修导航：搜索命中位置、完整性、附件消歧、取消与焦点、实际几何和打包入口。
3. 独立复审后端配对、权限、恢复和迁移；解决任何越权/重复提交/数据丢失风险。
4. 当前代码再跑合同、跨仓与真实浏览器验证，并逐项对照本表。真实来源许可/设备缺口不伪造为通过。
5. 只有发布范围通过后，才提交现有分支、完整 CI、签名 Release。网页升级能力和生产容量另行实时检查，不由此审查推断。

## 独立复审追加（仍为修复前）

两个既有子智能体使用本任务隔离目录复现，未改应用代码：

- **AUTH-01 / P1，实测：**已通过 Web 中间件的请求，在密码改变或该 Web session 撤销后继续运行，仍可经配对创建新的有效设备 grant。`extension_access.py:53–65` 的共用保留设备操作没有重新核对发行 session；短码与旧 PKCE 都需修复。真实隔离 PostgreSQL 两个否定断言失败。
- **MEM-01 / P1，实测：**索引 JSONL 一行的读取上限提高到默认 256 MiB 后，检查发生在整行分配之后。构造 96 MiB 合法 JSON 空白前缀，第一次工作区检查时 RSS 已增加 101,785,600 B，超过 64 MiB 工作区。应改成有界读取/逐步检查，不重新施加业务消息数/正文大小上限。
- **STATE-02 / P2，实测：**快捷 Context 设置先锁 preferences 再锁 preset collection；现有 Web 写预设顺序相反。真实 PostgreSQL 并发得到 `40P01` 死锁。需统一锁顺序，保留选择和完整性语义。
- **NAV-02 / P1，真实 Edge 合成来源实测：**浮层 iframe 已加载，但内容为空。动态 WAR 的 `getURL("frame.html")` 与消息实际 sender URL 不相同，`surfaces.js` 在已有正确票据/标签/父文档均匹配时拒绝 frame claim。不能仅放松身份检查；需兼容可信扩展实际 URL，同时保留一次性票据、frame、父 document 和路径校验。
