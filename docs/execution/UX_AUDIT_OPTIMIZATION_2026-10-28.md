## 保持条件状态

`STATE-SEARCH-SCALE` 没有在未测量时修改数据库查询。当前实现仍先取得候选
元数据、在 Python 中完成全局/项目 hash 折叠，再只水合当前页正文；这可能是
候选量很大时的成本，但没有本轮运行数据可证明是瓶颈。后续获得运行授权后，
应在隔离的合成 PostgreSQL 上记录候选量、重复比例、作用域、查询长度、耗时、
峰值 RSS 和执行计划，再以结果等价为前提评估窗口/数据库归组。

### 后续测量协议（未执行，不是性能结论）

- 只在新建、隔离、可丢弃的合成 PostgreSQL 数据库运行；禁止读取生产正文或
  将生产导入目录作为语料。不改变索引、migration、并发 worker 或生产设置。
- 固定随机种子和 canonical 合成语料，按候选规模 1k/10k/100k、跨对话重复比例
  0/50/90% 分组；覆盖全局、项目、单对话，命中稀疏/高频、中文、Unicode casefold、
  字面 `%`/`_`/反斜线以及各文档类型/角色/归档/owner 隔离；每组取首页与深页。
- 记录精确源码、PostgreSQL 版本、硬件/资源上限、样本参数和查询计划。分开记录
  数据库候选读取、Python hash 归组、当前页正文水合和匹配构造耗时；预热 5 次、
  重复 30 次，报告 p50/p95、峰值 RSS、候选数/折叠后数/页内水合数。
  `EXPLAIN (ANALYZE, BUFFERS)` 仅在该合成环境执行。
- 先证明候选读取/归组确实主导成本，再单独提出 SQL 窗口/归组候选实现；逐页比较
  顺序、代表文档身份、`occurrence_count/total/has_more`、目标和 canonical matches，
  对全局 hash 折叠与对话内消息身份分别验证，不能只比较结果数量。
- 若瓶颈不成立、结果不等价或小查询退化，则不改写。没有本轮测量数据，不声明
  延迟/内存收益，不把这一条件项列为已完成性能优化。
