## 已修复路径

1. **导入草稿写入**：不再 `asdict` 深复制整条对话的容器、再拼完整 JSON
   文本与 UTF-8 bytes；逐块写入并计算原哈希。单条 JSONL、格式和字节保持一致。
2. **导入提交重新准入**：预览成功不代表稍后提交时仍有内存。先用至多 1 MiB
   的读取测量下一条对话，超限在完整读取前拒绝；再按当前可用内存与既有
   固定余量/输入倍数准入，包括小记录。保持当前对话持久化期间的进程内准入，
   下一条前释放。低/未知内存明确失败，可通过既有任务重试；不盲目循环重试。
   提交循环与草稿转换器显式关闭嵌套生成器；即使保留失败异常的 traceback，
   也立即释放准入槽，避免依赖 GC 后才能处理后续任务。
3. **搜索索引重建**：完整正文/代码读取从 500 降至 8；待写数据按
   500 条或 2 Mi 文本字符提前 flush，避免少量长消息就积累巨大正文。
   这是软批次目标，不是单条消息上限。
4. **旧版 Markdown 下载**：保持旧版内容/标题/空白语义，改为逐条读取并直接写入
   现有 prepared-download spool；不再在溢写磁盘前先拼完整导出字符串。
   Markdown v2/CanJSON 的正文批次也降至 8。
5. **离线包**：消息改用 keyset 小批次；批次帧在下一批正文读取前释放。
   搜索正文读取同样限制为 8 条，而不是继续缓冲 100 条索引正文。
   批注/附件顶层数组逐条写入，附件 occurrence 只查询 RenderBlock ID，
   不为一个链接重复加载完整渲染块。v1/v2/v3 读取、v3 写出、Dexie v2 均未变。
6. **旧对话级 `.cr`**：导出不再一次保留全部历史版本/ID 列表，改用 SQL
   子查询与正文流。导入按记录数和约 2 MiB 原始 JSON 字节 flush；附件元数据
   两遍流式读取，事件/批注等不再整批积累。JSON 文档和 JSONL 行使用有界读取，
   启用既有压缩、展开、对象与 JSON 大小设置。超限明确拒绝，不截断数据；
   重复对象 ID 在再次落盘/扫描前拒绝；写出失败清理本次私有 staging。
   普通旧格式仍兼容，不增加协议版本。

## 小型合成分配对比

Windows Python 3.11.7 / SQLite；同一 129 条消息、每条 3 版本的合成 fixture。
从 Git 精确读取旧模块，与当前模块分别执行；计量期间不把整份下载留在内存。
`tracemalloc` 是 Python 分配，不是进程 RSS；下表不是 Linux/2 GiB 容量验收。

`.cr` 数据成员、旧 Markdown、离线 JSON 和草稿字节/哈希等价。
`.cr` manifest 的导出时间不作为字节等价断言。

这些单次微耗时不能作为生产吞吐结论。
这是明确的内存/查询权衡，没有声称所有导入/导出都会加速。

## 仍未验收与剩余风险

1. 本机 Docker Linux daemon 不可用；未启动 CI 代替。**未完成 Linux
   Docker PID 1、2 GiB/60 分钟持续负载、cgroup OOM/重启/RSS 平台验收。**
2. 单条巨大正文、很多历史锚点及大元数据仍有单记录成本；8 条批次不是固定字节
   上限。旧 `.cr` 过大单条记录会明确失败，不能把失败解释为数据已迁移。
3. 共享主机仍需足够内存；准入是检查/估计，不是 OS 保留。
   API/worker 为不同进程，各自的槽不能构成跨进程硬内存预算；
   阈值以下的其他解析请求和高并发下载尚未做压力验收。
4. 不改变现有“每条对话一行”的草稿协议；读入当前一条对话时仍需内存，
   只是先测量/准入并移除了写入的整份复制。
   没有 durable draft 的历史兼容提交分支仍会解析完整来源；当前新预览均生成
   草稿，本轮没有将该历史分支或 ZIP 目录元数据认定为已完成容量验收。
5. 没有生产交互、浏览器/PWA、全平台容量或“所有 OOM 已解决”的声明。
