## 最重要的三个结论

1. **先补上一轮的类型合同遗漏，再进入下一轮。** 这不是新功能，也不能用已有
   service-free 用例替代类型门禁。
2. **下一轮应先解决“该找到的没有出现”，而不是继续叠加匹配算法。**
   离线过滤晚于全库候选截断，在线当前对话又沿用了全局内容去重；两条链路都存在
   可由源码说明的漏结果条件。
3. **离线入口尚未统一。** 离线正文检索仍混入标题/类型字段候选，资料库侧栏仍丢失
   正文范围和附件/批注目标；同一内容从不同入口搜索，结果和落点不能保持一致。

建议将方向定为 **“检索召回完整性与离线入口一致性”**，拆成两步：
先修召回/过滤，再接齐资料库导航。不是扩建搜索平台，不承诺线上/离线排名完全相同。

### TYPE-01：上轮待收尾，不计为下一轮优化成果

`apps/web/lib/reader-data-source.ts:303` 新增读取 `item.message_version_id`，
而 `apps/web/lib/offline-db.ts:45–59` 的 `OfflineSearchDocument` 没有该属性，
`searchOffline` 的返回值正是此类型。服务端
`apps/api/app/services/offline_packages.py:854–871` 已输出版本字段；
前端 `apps/web/lib/offline-db.ts:701–710` 通过其余字段展开保留该值，并非导入丢失。
这会使按当前声明编译的新读取不成立，预期阻断类型门禁，但此处没有实际编译回执。
应补可选 nullable 字段，兼容缺字段的旧包和本机构建的私有文档；不新增 Dexie
索引或包版本，不通过 `any` 或断言绕过。验收还需未来获授权的 CI 类型检查。

### DATA-01：离线“无结果”可能只是目标被全库上限挤掉

`apps/web/lib/reader-data-source.ts:267–273` 对全库请求 `max(limit * 4, 100)`，
默认为 200，然后才按 conversation/type/role 筛选。worker 在
`apps/web/lib/offline-search.worker.ts:30–36` 已对各索引字段限量，再合并候选；
200 不是严格的合并总数，也不是当前对话的候选数。如果其他对话填满相关字段的
候选窗口，当前对话中有效结果就无法进入后续筛选。用户得到的空结果不能说明
其当前对话没有内容；把 4 倍改成更大常数只能移动失效边界。
建议把 scope/filter 送入 worker，在该作用域内排序/截断；保留全库搜索调用的
现有用途，不用无界取回所有文档来修补。

### DATA-02：同一对话的重复回答会失去独立消息落点

`apps/api/app/services/search/search_service.py:210–236` 使用
`("message", content_hash)` 作为分组键，没有区分是否传入 `conversation_id`。
`apps/api/app/services/import_pipeline/canonical_draft.py:88–92` 的 hash 只绑定
规范化文本和角色，不绑定消息身份或位置。因此同一对话内相同角色、相同正文的
多条消息只保留一个代表，`occurrence_count` 仍是一个会话；随后只为这个代表构造
正文 matches。用户无法通过当前对话的上一/下一命中走到其他相同回答。
建议仅在明确的当前对话搜索中保留不同消息身份；全局/项目搜索的跨会话折叠和
会话计数先维持现状。已有 `apps/api/tests/test_search_api.py:279–288` 约束全局
两对话折叠，不应为了新行为删除或改弱它。

### DATA-03：正文结果不能只因标题或类型相同而成立

`apps/web/lib/offline-search.worker.ts:25,31,44` 索引并联合查询 `title/body/type`。
当前对话调用没有传递字段域；data source 在 `:285–294` 即使没有正文 match
也保留结果并回退到开头摘要。仅在标题出现的词，或只命中内部类型值 `message`
的查询，因此仍可贡献所谓正文结果。在线已有相反的限定与
`apps/api/tests/test_search_api.py:224–231` 的标题不冒充正文用例。
建议明确字段域：当前对话正文不通过标题/类型字段召回；资料库全局仍可搜标题，
附件文件名和批注评论仍保留自己的检索域。不能简单删除所有 `matches=[]` 的结果，
因为旧离线包缺 canonical block 时仍应允许真实内容的消息级结果。

### NAV-01：离线资料库侧栏没有接上上一轮目标合同

`apps/web/features/offline/library-shell.tsx:758–761` 的结果激活只交给 `onOpen`
四个旧参数；`:402–410` 的 URL 构造只保留 conversation/message/block/start。
没有传 message version、block ID、范围终点、附件或批注身份，也没有按文档类型
选择目标。附件/批注结果只能走普通对话/消息打开，正文也没有查询对应的精确范围。
建议在有 canonical block 时复用上一轮范围映射和校验，按类型生成目标；
缺失数据安全降级，不从摘要伪造位置。保留 `/library?conversationId=…` 路由，
**不能直接照搬返回 `/conversations/…` 的在线 href**。正文、附件、批注纳入本批；
description/notebook 等其他类型保留现有行为，不趁机新增工作区。

最小优先收尾为 TYPE-01，而提高搜索 limit、禁用去重、抹除筛选或改弱用例都不是验收。

回归层次：真实查询/分组逻辑用例 → 现有 Web 类型门禁 → 既有离线浏览器专项。
`scripts/ux/offline-search-readiness.test.mjs:16–17` 明确使用 Worker transport
