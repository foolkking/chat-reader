分享入口已经采用分组设置和渐进显示，无需重新设计外观。当前最值得修复的是设置并发覆盖：编辑一个标题也会提交旧权限，可能重新暴露刚在另一窗口关闭的私人内容。批量撤销的服务端逐项事务是正确的，但前端重试单项会替换全部反馈，使其他失败项消失。按有效状态分页时，撤销最后一页所有项目后也不会自动返回有效页，形成假空列表。这些都是有具体后果的缺陷，不是风格偏好。

## 实施边界

- 不直接用 `updated_at` 作编辑基础版本：`share_service.py:179` 会在访问分享时更新它，访客阅读不能导致编辑冲突。
- 使用设置字段、密码版本和撤销状态的确定性不透明摘要；排除访问计数／访问时间。旧客户端不携带基础版本时保留兼容行为，新 UI 携带基础版本。无需数据库 migration。
- 授权先于返回最新设置，新增本人分享详情读取也必须使用现有 OwnershipScope；不能通过分享身份绕过账户隔离。公共 token 语义不变。
- 服务端行锁内重新读取并比较，避免 SQLAlchemy 已加载对象遮蔽并发更新。批量撤销仍使用现有逐项事务和幂等事件。
- UI 明确区分冲突与网络失败。密码不回显到比较、日志或证据。关闭和刷新原有未保存提示继续保留。

## 验收

1. 两个真实客户端同一基础版本并发保存，仅一个成功；另一项冲突且不覆盖权限。访客访问不引起冲突，撤销不能恢复，其他账户不能获取最新内容。
2. 用户修改标题期间另一设备关闭额外内容：旧保存失败；比较后保留个人标题并采用服务器未修改字段，实际公开页面也符合新权限。
3. 三个真实分享逐项撤销，两个失败；重试其中一个后另一失败仍可见并可重试。检查数据库状态／公开链接失效，不伪造成功响应。
4. 21 项有效分享撤销最后一页，自动回到剩余 20 项；375/768/1440、中英文、键盘焦点和截图检查。
5. 跑对应 API、真实 PostgreSQL 并发、Share 浏览器专项、lint/typecheck/build；记录初次失败、跳过及未执行范围。
