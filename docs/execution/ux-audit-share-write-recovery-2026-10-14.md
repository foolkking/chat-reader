# 分享写入恢复审查 — 2026-10-14

源码审查确认：

- 创建、有效期、密码、重新生成和撤销失败都直接展示异常的 `.message`，可能
  把 API detail、传输错误或实现文本作为界面文案。
- 创建／更新／重新生成／撤销成功后，面板还会读取分享列表；这个 GET 失败
  会被外层 `catch` 当成写入失败，导致已完成的写操作被误报。
- 创建和其他写入遇到网络或服务端异常时没有区分“请求被拒绝”和“结果未确认”，
  用户可能立即重复创建、更新或撤销。

## 发现与决定

| ID | 类型／严重度／证据 | 用户影响与处理 |
|---|---|---|
| SHARE-WRITE-ERR-01 | Defect / High / Observed(code) | 写操作直接展示原始异常。按状态和操作类型提供稳定的中英文恢复文案。 |
| SHARE-WRITE-STATE-02 | Defect / High / Observed(code) | 写入已确认但列表刷新失败会被误报为写入失败。区分写入确认与刷新失败，并保留已生成链接。 |
| SHARE-WRITE-RECOVERY-03 | Defect / High / Observed(code) | 网络／5xx 等异常的结果可能未知，立即重试会造成重复或误操作。提示先刷新列表核对，不自动重放写请求。 |

## 实现边界

- 只修改分享面板的用户反馈和刷新结果判断；不改变分享 API、链接、权限、
  过期时间、密码或撤销语义。
- 已知 4xx 状态给出可操作的稳定提示；网络、5xx 和其他未知写入结果明确
  为“未确认”，不声称必然失败或成功。
- 列表刷新仍是单次只读请求；不增加轮询、依赖或服务器资源。

## 实施记录

`apps/web/features/sharing/share-panel.tsx` 现在将创建、设置更新、密码更新、
重新生成链接和撤销的异常映射为稳定的中英文文案，不再直接显示底层异常。
已知权限、会话、资源不存在、并发变化、已撤销／过期、输入无效和限流状态分别
给出对应方向；网络、5xx 和未知写入结果明确提示“尚未确认”，要求先刷新列表
核对，不自动重放写请求。

写入成功但随后分享列表刷新失败时，界面现在保留已生成链接或当前操作上下文，
并明确说明写入已完成、只读列表刷新失败；不再把成功写入误报为写入失败。
列表刷新仍使用同一个查询的单次 `refetch`，没有增加轮询、依赖或服务端资源。
