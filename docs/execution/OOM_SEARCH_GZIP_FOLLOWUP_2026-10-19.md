## 已修复

### 1. 附件索引不再保留整批大元数据

旧索引通过 `.all()` 同时加载所有 Attachment、AssetObject、occurrence 和 Message，
其中附件 JSON metadata、occurrence caption 并不参与索引，却会随文件数累计。
随后还保留全部衍生物历史及对象字典。

新查询只投影索引需要的列，以八条读取窗口消费；最新 ready 文本衍生物在同一
SELECT 中关联，不按 occurrence 增加应用层查询。不读取 metadata/caption。
文本文件仍最多读取 256 KiB；对象不可用或文件缺失时保留文件名搜索。

另修复了倒序衍生物列表写入字典后被旧记录覆盖的错误：现在按创建时间和 ID
确定最新 ready 记录，不把 pending 版本当作可用文本。索引权属、当前消息过滤、
文件名与 occurrence 身份不变，不改源文件或消息正文。

### 2. 批注重建与旧索引清理

旧路径读取 200 条带完整摘录/评论的批注，结束时又 `.all()` 读入全部批注索引正文；
待删除的 ORM 实体还会一直保留到 flush。

现在批注正文窗口为八条；清理按 200 个 ID 的 keyset 页处理，不读取 SearchDocument
正文，按页删除并同步调用方已持有的 ORM 身份。普通同步和带逐条 savepoint 的
backfill 共用这条清理路径。统计、幂等、保留非批注文档和外层回滚语义不变。
backfill 的对话 ID 也不再一次收集完整列表。

这不是严格 O(1) 内存算法：当前对话的 `seen` ID 集合仍随批注数增长，单条大批注
仍有其自身成本；被移除的是整批重复正文与大对象。

### 3. gzip 展开量不能再只按压缩字节估算

旧准入主要估算来源文件字节。约 20 KiB 的 gzip 可以在合法压缩比内展开到约
2 MiB；合成零余量探针下，旧解析仍成功，证明小压缩输入可以绕过重型输入检查。
该 fixture 使用 1 MiB heavy threshold / 64 MiB reserve 便于验证，不改变生产
10 MiB / 512 MiB 默认值，也没有主动制造 OOM。

新 JSONL 读取每次不超过 64 KiB，保留既有行大小、压缩比和行结尾语义。
gzip 累计展开量超过“压缩字节与 heavy threshold 的较大值”后，以既有
固定余量 + 展开量 × 配置倍数复查 headroom，之后每增加约 1 MiB 再检查。
大记录在完整构造/JSON 解码前即可拒绝；小行累计增长同样不能绕过复查。

来源识别的 gzip manifest 也复用该有界路径，避免正式解析之前就先解码大表头。
复查不重新获取外层 parser 槽，避免 worker/预览已持槽时自我等待。
这仍是保守估算，不是 OS 预留、全局跨进程内存预算或无限大小承诺。

资源不足/未知：

- 普通预览返回原有 `UPLOAD_MEMORY_PRESSURE` / HTTP 429 和 `Retry-After: 15`；
- 自适应验证不再将该 ValueError 子类吞成“映射错误/格式漂移”；
- 后台任务明确失败、回滚分析变更并保留来源；余量恢复后可重试原任务 ID；
- 不创建自动忙重试，不把未完成内容伪装成成功预览。

### 4. 顺带修复内置 CanJSON 的真实后台失败

真实 worker 回归先于内存检查暴露 `KeyError('locator')`：
CanJSON v2 原生识别有意没有通用 JSON selector，却被 `default_mapping` 强制索引
`locator/role/content`。现在这些建议字段允许缺失，仍由已匹配的内置 normalizer
读取真实记录。普通自定义 JSON 的 selector 校验没有移除。
修复后同一合成任务经历“资源失败 → 原文件保留 → 原 ID 手动重试 → READY”。

吞吐结论，没有据此新增数据库索引。

既有比率限制内。零余量探针下，旧路径不查内存并解析完整 2,097,446 字节消息

- 没有重跑全量 Web/PWA/浏览器：本轮没有前端修改；字段消费做过源码检查，
  不把它称为挂载交互通过。

- 小输入并发和 API/worker 跨进程竞争不能靠一次 headroom 探针完全消除。
  本轮没有宣称“所有 OOM 已解决”，也没有用局部耗时声称导入整体加速。
- 本轮不授权发布。以后发布仍须按现有 API/PostgreSQL、Web/PWA、镜像及受限
  生产验收门禁执行；schema 仍为单一 0052。
