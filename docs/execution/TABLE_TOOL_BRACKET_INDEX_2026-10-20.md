# 表格括号索引、围栏扫描与异常嵌套输入 — 2026-10-20

状态：本地持续优化，目标保持活动且无限预算；不推送、不启动 CI、不部署。
不改变依赖、API、migration、canonical 数据或导出/离线协议。

## 定位与取舍

先测量两组接近工具规模上限的合成表格：10 列 × 4,000 数据行约 397 KB，
200 列 × 248 数据行约 499 KB。普通序列化中位数约 2–4ms，并未证明需要
额外缓存，所以没有新增序列化缓存或改造编辑状态架构。

实际发现的异常路径是单元格中重复未闭合 `![`：旧括号分类从每个嵌套图片
开头重新扫描剩余文本。2,000、4,000、8,000 UTF-16 单位的本机三样本中位数
分别约 **3.49、13.36、49.48ms**，长度翻倍耗时接近四倍。这里只测小输入，
没有让旧实现处理 240,000 单位，也不能把此问题当成服务器崩溃/OOM 的证据。

## 修复与数据边界

- 用惰性后缀索引替代逐开括号扫描；两个线性遍历，一次操作内复用。
- 仅需要分类时分配一个 `Int32Array`，每个 UTF-16 单位四字节，加一个哨兵；
  不做进程级缓存，不保留历史正文，也不新增任意嵌套深度截断。
- 反向计算“从该偏移、独立正常内联上下文出发的第一个未配对闭括号”，保留
  原代码跨度、成对转义、图片 alt、引用与脚注判定。不能用全局代码栈代替：
  前面被数学解析跳过的文本可能包含反引号，后面链接仍须独立分类。
- 解析行与单元格竖线编码/解码共用索引策略；测试对照旧规则，而不是放宽
  语法来让异常输入看起来合法。
- 单元格输入长度已必然超过原有 1 MiB UTF-8 工具预算时，在索引/转义前拒绝。
  继续使用现有超限提示并保留上次接受的草稿；最终完整 UTF-8 大小校验不变。
  未超限的无效 Markdown 仍完整保留，可编辑修复，但不能应用。

括号修复检查点的三样本中，8,000 单位中位数约 **1.63ms**，240,000 单位约 **18.22ms**。
这是未节流 Node 合成观察，不是浏览器交互 SLA，也不是跨设备受控性能验收。
普通大表富渲染的 main-thread long task 仍存在。

## 随后发现的围栏回溯

继续审查发现，代码围栏正则将重复引用、可选空格和必需围栏标记放在同一
模式里；深引用的普通正文不含围栏时，会尝试大量等价空白分配。
独立 worker 的修复前样本：20 层引用、总长 84 单位，检查约 **320ms**；
24 层触发 **2 秒**诊断 watchdog。新回归的 6,000 层前缀在修复前也触发
**10 秒**防挂死 watchdog，结果为 1 通过、1 失败、24 个名称筛选跳过，
不是通过门禁。

现在逐物理行读取前缀，再检查反引号/波浪线及 info string，不组合成会回溯
的整行模式，也不创建全部前文的行数组。代码示例保护、信息串不能当闭围栏、
围栏字符/长度、引用和列表前缀保持原语义。500 个有界 LF/CRLF 样本与旧
实现逐一比较；6,000 层引用的普通正文、开围栏和闭围栏分别验证。
修复后单次纯函数观察中，6,000 层约 **1.53ms**；包含首次运行和环境噪声，
仅用于诊断，不作为真实交互延迟承诺。

## 后续微调

继续审查表格输入路径后，将纯转换模块的 `TextEncoder` 改为模块内复用的
单实例，避免每次范围检查、规范化或替换都重复构造编码器；没有引入缓存
表格正文或改变 UTF-8 限制。

富预览的结构校验现在区分“仍在追赶”与“已完成但没有渲染成同形状表格”。
后一种情况在对话框内显示明确错误并把原因关联到“应用”按钮，避免用户只
看到一个无说明的禁用按钮；原文、草稿和应用保护规则不变。最终源码的
聚焦、Chrome、lint、非增量 typecheck 和单 worker build 均重新验证。
