## 3. 功能详情

### WEB-15 · 带来源的片段引用复制

- **需求问题：** 用户把内容贴到笔记、文档或其他工具时，是否经常忘记它来自哪里，
  需要回到原文核对？
- **现状证据：** `apps/web/features/conversations/reader-markdown-copy.tsx:9–44`
  把选区序列化为 Markdown 并写剪贴板；`message-item.tsx:161–169`
  已有整条消息复制和书签。这条路径未自动附带来源标题及稳定定位链接。
- **最小版本：** 显式“复制为引用”，生成选区正文、来源标题和私有 Reader 锚点链接；
  普通复制保持原行为。可先做单消息内选区，不承诺跨虚拟窗口选择。
- **边界：** 私有链接不授予访问权，清楚提示接收人需要原有权限；不自动创建 Share、
  公共图片链接或把 token 放入引用。引用文本与锚点版本对应，变更后安全降级；
  剪贴板失败提供手动复制。
- **验收／价值验证：** 中文、代码和表格引用不混入按钮文案；链接回到正确范围。
  复制本身零内容／分享写入，未授权接收人仍无法读到私有正文。
  与“复制后自己寻找出处”的合成任务比较操作步骤。

### WEB-16 · 搜索命中连续阅读

- **需求问题：** 用户需要核对很多命中的上下文时，是否反复“打开结果—返回列表”，
  难以记住读到第几条？
- **现状证据：** `apps/web/features/search/search-page.tsx:40–46,88–99`
  管理单个活动结果并路由到 Reader；已有结果页键盘上下移动，但本次所查路径未见
  Reader 内跨搜索结果的“上一条／下一条”会话。不要误称现有浏览器返回完全不可用。
- **最小版本：** 明确的“从搜索阅读”模式：保留查询、活动结果和已加载队列，
  Reader 显示上一命中／下一命中／返回结果。首版不冒充已加载整个搜索总数。
- **边界：** 以 document ID 和精确目标定位，不以数组序号充当持久身份；
  重复正文、同对话多个命中各自保留。目录跳转后仍能回到当前搜索命中；
  查询变化、权限失效和对象删除不能继续显示旧账号队列。URL 不携带正文。
- **验收／价值验证：** 连读多个命中并返回后，筛选和结果位置可恢复；
  后页插入／去重不会跳错；Reader 沿用原导航事务，不把程序化滚动记为用户阅读。
  这不是 WEB-07 的批量写操作，首版不加入批量按钮。

### WEB-17 · 直接粘贴文本导入

- **需求问题：** 用户手里只有一段 Markdown、纯文本或结构化对话文本时，
  是否值得省掉“另存文件再上传”的步骤？
- **现状证据：** `apps/web/features/import/import-panel.tsx:399–417`
  当前入口是拖放／选文件；新建对话的双消息表单并不等于多轮文本解析。
  本次所查导入入口未见直接粘贴整段记录后预览的流程。
- **最小版本：** 与“选择文件”并列的粘贴页，显式提交分析；复用现有格式识别、
  角色校验、预览、ImportDraft 和 commit，不新建另一套解析器。
- **边界：** 不自动读剪贴板；用户未点分析前不上传。规模和权限限制与文件入口一致；
  角色边界不明时要求确认或降级，不能把普通散文强行切成问答。
  输入失败保留草稿，正文不进入日志；提交未知时沿用原幂等恢复。
- **验收／价值验证：** 同样的 UTF-8 内容通过文件和粘贴得到等价预览；
  空白、超限、多轮、代码块内伪角色标记及取消流程均清楚；
  先验证用户确实有剪贴板导入任务，不默认改掉原文件入口。

### WEB-18 · 表格复制为 TSV／导出 CSV

- **需求问题：** 用户是否经常想把回答里的表格放进 Excel 或其他表格工具，
  而不是复制出带竖线的 Markdown？
- **现状证据：** `apps/web/features/conversations/markdown-table.tsx:5–25`
  是显示组件；`reader-markdown-copy.tsx:36–44` 主要写 Markdown。
  已有源码表格编辑与 Office 文件预览，不能等同于正文表格的结构化数据复制。
- **最小版本：** 单张正文表格提供“复制为表格（TSV）”和 CSV 下载；
  可选择是否带表头，明确处理单元格换行。普通 Markdown 复制继续保留。
- **边界：** 从完整表格的数据／语法结构取值，不只抓屏幕可见 DOM；
  数字前导零、日期样式和空单元格不擅自改值。对 `= / + / - / @` 等可能被表格软件
  当公式的内容提供明确的安全文本选项，不宣称 CSV 能保证所有软件的显示类型。
  HTML、公式或脚本不因复制而执行。
- **验收／价值验证：** 引号、逗号、制表符、多行、中文和空值往返结构正确；
  大表格不漏行，带公式前缀有明确提示。用复制到表格工具的任务验证需求；
  本轮没有操控 Excel 或生成电子表格。

### WEB-19 · 轮次折叠与角色聚焦阅读

- **需求问题：** 很长的往返对话中，用户是否需要临时收起已看过的轮次，
  或重点阅读回答而保留问题上下文？
- **现状证据：** `apps/web/features/conversations/message-item.tsx:161–185,241–260`
  有复制、书签、选择、编辑和正文渲染，本次所查操作中没有轮次级折叠入口。
  搜索的角色筛选不是 Reader 显示模式；已有代码折叠等局部行为也不等价于轮次折叠。
- **最小版本：** 先做显式折叠单个完整轮次，保留问题摘要、消息数量及展开按钮；
  再按需求评估“回答优先”显示。它是视图状态，不生成新正文版本。
- **边界：** 不改变完整轮次数据合同、不把被折叠消息从计数、导出或权限范围删除。
  搜索／TOC／批注跳转应先展开真实目标再测量定位；折叠恢复用稳定身份，
  不能以屏幕行号保存；不把布局补偿当用户滚动。首版只承诺同一阅读会话内状态。
- **验收／价值验证：** 折叠前后锚点稳定，长轮次、虚拟窗口切换和目标命中都能正确展开；
  键盘能操作并获知状态。若增加模式反而让用户漏读上下文，应只保留逐轮折叠。

### WEB-20 · 拆分／合并来源与派生去向

- **需求问题：** 用户过几天再打开拆分或合并结果时，是否需要知道“从哪几段资料来，
  原始记录还在哪里”，而不只依赖新标题？
- **现状证据：** `apps/api/app/services/editing/message_edit_service.py:503–525,570–588,674–686`
  记录合并来源和拆分来源事件；`apps/api/app/models/conversation_event.py:13–25`
  有事件及 payload；`apps/api/app/api/routes/conversations.py` 已有 conversation events
  读取接口。本次所查 Reader 操作入口未见面向用户的来源／派生导航。
- **最小版本：** 对话信息中的“来源与派生”只读列表：操作类型、发生时间、
  有权限的来源／结果链接。仅解析已有明确事件，不引入图数据库或推断关系。
- **边界：** 历史事件不是当前访问凭证；读取每个关联对象时重新检查 owner，
  删除／无权对象显示不可用，不泄漏标题。导入的外部来源 ID 不直接当作本地 ID。
  没有历史事件时说明“无可追溯记录”，不靠同名或正文 hash 猜关系。
- **验收／价值验证：** 多来源合并和一拆二都能逐项追溯；原记录删除、归档、
  导入重映射后链接不串到其他记录。与 WEB-08 对照阅读可组合，但不依赖其先实现。

### WEB-21 · “上次阅读后新增了什么”

- **需求问题：** 用户回来时是否需要直接找到新增消息，而不是重新浏览长对话，
  也不把每次修改描述或批注误认为正文新增？
- **现状证据：** `apps/web/features/reading/recent-items.tsx:35–63`
  展示继续阅读位置；`conversation-list.tsx:611–615` 按更新时间／阅读时间展示活动。
  `apps/api/app/models/reading_position.py:25–40` 保存位置和同步 revision，
  不是整段对话的“已阅内容快照”。
- **最小版本：** 先定义个人“上次打开时的正文变化基线”，只提示新增消息数量并可定位；
  较复杂的旧消息修改清单后续再评估，不一开始建立完整变化中心。
- **边界：** “打开过”不等于“全部读完”，不能覆盖 WEB-03 的手动已读意图。
  不单凭 `updated_at`、`offline_revision` 或导入原始时间判断新增；
  批注、附件改名、排序不应制造新消息提示。删除、版本切换、迁移后也需有明确语义。
- **验收／价值验证：** 新增消息能定位到第一处；仅改标题／批注时无误报；
  导入的旧时间消息仍按系统实际新增语义处理。缺失旧基线时显示未知而不是编造数量。
  这项需数据合同支持，不能只加一个“有更新”角标就宣称完成。

### WEB-22 · 可选冻结分享：后续编辑不改变已经交付的内容

- **需求问题：** 用户把资料发给别人作为讨论或交付依据时，是否需要“对方一直看到
  当时那一版”，而不是跟随来源更新？
- **现状证据：** `apps/api/app/models/share.py:25–32`
  保存范围／消息 ID 及附加内容开关；`services/sharing/share_service.py:657–664,710–721`
  按当前非删除消息及 `current_version_id` 读取。现有 Share 是受权限约束的实时投影，
  不是冻结正文。这本身是有效的产品选择，不记为漏洞。
- **最小版本：** 创建时明确二选一“跟随原文更新／冻结本次内容”，先评估有界的
  只读快照。预览 WEB-05 解决“现在会分享什么”，本项解决“以后是否变化”，两者不同。
- **边界：** 老 URL 继续原语义；撤销、过期、密码仍对快照生效。
  正文、附件、目录、私人内容需共同定义版本边界，不能只冻结消息 ID。
  来源删除后的撤销／保留规则和快照空间成本必须先决策；
  不能因快照而默默延长敏感内容保存，也不能承诺撤回接收人已经复制的内容。
- **验收／价值验证：** 创建后编辑、删除、增添来源内容均不偷偷改变冻结结果；
  实时链接仍按旧合同工作，失权／撤销严格拒绝。若用户实际上只需打印稿，
  优先 WEB-06，不同时建设两套交付机制。

### WEB-23 · 批量标题修整预览

- **需求问题：** 大批导入后，用户是否需要统一去掉无用前缀、添加项目标记，
  而不愿逐条打开改名？
- **现状证据：** `apps/web/features/conversations/conversation-metadata-dialog.tsx:17–44`
  以单对话／单字段管理草稿和原值，且区分 title 与 display_title；
  `conversation-list.tsx:618–677` 的批量操作不含标题修整。
- **最小版本：** 对已明确选择的对话提供字面前缀添加／删除或逐项改名，
  展示“原名 → 新名”、未变化项和空标题错误；确认后冻结选择及每项原值。
  首版不支持任意脚本、正则替换或 AI 自动起名。
- **边界：** 不因翻页或列表刷新加入其他对话；他处已改名的项停止并核对，
  不覆盖新值。处理存储标题与展示标题的一致性，明确部分完成与未知结果；
  不能在丢响应后盲目再应用一次前缀，也不承诺没有合同支撑的一键全部撤销。
- **验收／价值验证：** 重复标题、Unicode、空结果、同一前缀已存在、并发改名、
  真实提交后丢响应分别覆盖；预览和取消都零写入。先核对是否有稳定的重复改名任务。

### WEB-24 · 可跳过的合成示例体验

- **需求问题：** 新用户是否因为没有合适的导入文件，无法快速判断阅读、目录、
  搜索、公式、代码和批注功能是否适合自己？
- **现状证据：** `apps/web/features/conversations/conversation-list.tsx:388–405`
  的首次空状态主要引导导入；`features/import/import-panel.tsx:399–424`
  提供文件入口和格式帮助。本次所查路径未见可直接体验的合成对话。
- **最小版本：** 可选“查看示例”，使用明确标为示例的短合成资料，展示少量关键能力；
  如用户想保存，再显式进入现有导入流程。不要求看完，不做多屏强制教程。
- **边界：** 不取任何真实用户对话作演示；不自动污染库、最近记录或后台队列；
  示例不携带可访问生产资源的链接。编辑／批注若需持久化，先明确创建用户副本，
  不能把示例行为误显示为已经保存。
- **验收／价值验证：** 空库仍保持空库直至用户明确导入；离开示例不丢已有草稿；
  演示范围和真实功能一致。先观察能否减少“我要先准备什么文件”的疑惑，
  不用装饰性轮播代替实际体验。

## 4. 建议取舍

### 本轮相对适合先验证

1. **WEB-17 粘贴导入：** 可以复用既有解析与预览路径，需求边界清楚。
2. **WEB-15 引用复制：** 对外复用内容时直接解决出处丢失；私有链接语义必须醒目。
3. **WEB-18 表格复制：** 聚焦一种具体输出，不引入新的长期数据模型。
4. **WEB-16 连续阅读命中：** 对频繁检索用户有潜在收益，但必须先保证导航与返回状态。

这是新一轮内部的验证顺序，不自动推翻第一轮保存搜索、版本对比等建议。
建议从两轮合计 24 项中先选 **2–3 个真实任务频繁的功能**，而不是把候选池变成排期。

### 先明确使用频率／数据合同，再投入

- WEB-20 来源导航可从已有事件做只读入口；先核查历史记录完整度。
- WEB-23 批量标题处理先要有真实命名规则，不能为了批量而批量。
- WEB-19 折叠会影响 Reader 布局与导航，WEB-21 更新提示需要新的正文变化语义，
  都不是只加开关或角标。
- WEB-22 冻结分享是明显的存储、隐私和生命周期扩展，优先级应由交付需要决定。
- WEB-24 示例适合新用户，若主要用户都是有现成资料的熟练用户，可先不做。
