# Web 用户功能候选 — 2026-10-29

## 1. 状态、方法与边界

**候选审查已写完；仅需求候选，不是已批准设计或实施承诺。**
本报告承接[恢复一致性复审](ux-audit-next-batch-followup-2026-10-29.md)，
回答“除了修错，Web 用户还可能需要哪些功能”。

依据是当前工作树的路由、组件、API 和现行功能清单；未开展用户访谈、使用率分析、
浏览器测试或 web search。**现有能力是源码观察，预期用户收益是需求假设。**
以下不是 14 个“已经证实的产品缺陷”，不能把功能数量当作质量分数。
不修改功能代码，不运行本地门禁、CI、迁移、提交或部署。

### 当前路径与可扩展位置

```text
导入 → 全部对话／项目 → Reader → 批注／精选
                     ↘ 搜索 → 精确定位
Reader → 分享／导出
资料库 → 全部／项目／单对话下载 → 离线 Reader／同步中心
```

优先补“反复找同一组内容、回看整理成果、写前先比较、发出前先检查”的闭环，
而不是新建第二套 Reader、搜索引擎或任务系统。

### 已有能力，不重复包装成新需求

- 全局搜索已经支持类型、角色、项目、日期和活动／归档范围。
- 已有书签、批注、精选笔记；候选是**跨对话的发现和复用入口**。
- 已有消息版本切换、恢复、删除和噪声差异预览；候选是**通用只读版本对比**。
- 已有分享密码、期限、所选消息、私人内容开关及创建后的链接打开。
- 已有项目／全部离线下载、增量更新、附件可用数量、离线启动状态和同步冲突处理。
- 已有归档、确认后的硬删除、搜索快捷键、帮助诊断和归档导入重复提示。
- HTML／PDF 导出、标签等属于当前清单的明确非现有能力；下面只是提出重新评估，
  **不因列入报告就改变产品范围或兼容合同**。

## 3. 功能候选详情

### WEB-01 · 保存搜索与命名视图

- **场景／假设：** 用户经常重新输入相同关键词，再组合项目、角色、日期等条件；
  让用户保存“项目 A 的代码问题”等命名查询，可能比增加筛选项更有用。
- **现状证据：** `apps/web/features/search/search-page.tsx:30–62,77–85` 已把条件
  放入 URL；`search-box.tsx:7–28` 保留输入和浏览器返回语义。本次所查入口没有
  命名查询列表。现有 URL／浏览器收藏可以复用，不声称完全无法保存搜索。
- **最小版本：** “保存当前搜索”、命名、重命名、删除、再次打开；保存条件而非
  结果快照。先仅支持已有过滤项，不以“智能视图”名义承诺自动分类或语义搜索。
- **边界：** 第一版明确本机还是跨设备；本机数据须账号隔离、支持清除。
  关键词可能敏感，不写入诊断日志；失效项目要提示，不能静默变成全部项目。
- **验收／价值验证：** 保存后重开条件完全一致，权限变化仍安全；
  用重复检索任务比较重新设置条件与调用视图的步骤，而不是声称搜索变快。

### WEB-02 · 全局书签／批注收件箱

- **场景／假设：** 用户记得自己标记过重点，却忘了在哪个对话；希望不输入关键词
  就能按项目、颜色、类型或待复核状态浏览自己的整理成果。
- **现状证据：** `apps/web/features/annotations/annotation-workspace.tsx:76–129`
  以 `conversationId` 为范围；`apps/api/app/api/routes/annotations.py:36–53,146–184`
  的列表与笔记接口围绕单对话。搜索已有 annotation 类型，但
  `search-page.tsx:62` 需要非空关键词，不能等价于全量书签收件箱。
- **最小版本：** 一个服务端分页的只读聚合入口，显示来源、摘录、批注类型和锚点状态；
  点击复用精确 Reader 定位。先不引入跨对话写入／新笔记模型。
- **边界：** 不能先下载全部对话批注再前端过滤；按 owner 查询，私人批注不因聚合进入
  Share。孤立锚点保留摘录并标待复核，不假装仍能精确跳转。
- **验收／价值验证：** 无关键词能找回跨项目书签；分页无串账号、重复和静默遗漏；
  合成“记得标过但忘记来源”的任务验证找回路径是否更短。

### WEB-03 · 待读清单与手动已读状态

- **场景／假设：** 最近打开不等于读完，归档也不等于已读。用户可能想把一段长对话
  留到以后处理，并明确标记完成。
- **现状证据：** `apps/web/features/reading/recent-items.tsx:13–63` 提供最近位置与
  阅读进度；`apps/api/app/models/conversation.py:23–40` 的状态主要用于活动／归档，
  本次所查路径未见独立的待读队列及手动阅读状态。
- **最小版本：** 加入／移出待读、手动标已读／未读、按加入时间浏览；
  打开时继续使用现有真实锚点，不另建位置记录。
- **边界：** 程序化滚动、搜索跳到底部、预览或打开附件均不能自动标“读完”；
  不复用归档状态，不默认提醒用户或制造通知。跨设备同步需先明确数据合同。
- **验收／价值验证：** 只允许明确动作改变阅读状态；待读与归档互不误改；
  用长文中断任务核对用户是否真的需要清单，而非仅需要更易找到“继续阅读”。

### WEB-04 · 不改正文的版本对比

- **场景／假设：** 用户只想看“这次编辑／清理改了哪里”，不想为了查看上一版
  先改变当前正文。对经常编辑或使用噪声清理的人可能尤其有价值。
- **现状证据：** `apps/web/features/editing/version-history-panel.tsx:54–100`
  提供版本切换和当前版本文本；`use-message-version-history.ts:235–267`
  的 select 调用写接口。已有 `cleanup-change-preview.tsx:7–25` 是基于已知删除范围
  的噪声前后对照，不能直接等价成任意两个历史版本的通用 diff。
- **最小版本：** 选择两个历史版本，展示只读增删差异、版本时间和编辑原因；
  “设为当前版本”保持独立明确按钮。大文本显示有界差异或分段加载。
- **边界：** 比较本身零写入，不改变当前版本、阅读位置或批注锚点。
  字符比较处理 Unicode、代码和表格；附件引用应显示为引用变化，不能误当文件内容相同。
- **验收／价值验证：** 连续比较不同版本时写接口调用数为零；发现变化后仍能退出回原处。
  先验证是否帮助用户判断恢复哪版，再考虑复杂并排渲染。

### WEB-05 · 分享前访客视角预览

- **场景／假设：** 用户在发链接前希望确认对方究竟会看到什么，尤其是所选消息、
  附件文件名、批注、笔记和到期设置。
- **现状证据：** `apps/web/features/sharing/share-panel.tsx:23–40,172–200`
  有内容开关、创建按钮及创建后的打开链接；`share-editor.tsx:160–196`
  已有内容和访问摘要。本次所查流程没有生成有效公共链接前的访客内容预览。
- **最小版本：** 创建前提供只读预览和包含／排除清单；确认范围后再创建。
  尽可能复用 Share 的服务器投影和 ReaderDataSource，而不是用 owner 正文简单隐藏按钮。
- **边界：** 预览不生成长期有效 token、不增加访客访问统计；被排除的正文、附件、
  私人内容在预览响应中也应排除。已创建链接的打开与密码流程继续保留。
- **验收／价值验证：** 相同选项下预览与真实访客结果一致；测试所选消息、
  私人批注关闭、附件拒绝、密码和过期。用合成敏感段落检查用户能否在分享前发现误选。

### WEB-06 · 面向打印／PDF 的完整阅读稿

- **场景／假设：** 用户需要会议材料、纸面校对或可递交的阅读稿，Markdown 下载
  不总能直接满足排版用途。
- **现状证据：** `apps/web/features/exporting/export-panel.tsx:110–114`
  主要提供交给 AI、CanJSON、Markdown；`docs/system/FEATURE_INVENTORY.md`
  明确未包含 HTML／PDF 导出。Reader 使用完整轮次窗口，当前 DOM 并非整段对话。
- **最小版本：** 先提供明确范围的打印阅读稿，含标题、角色、章节、页码及代码折行；
  再评估直接 PDF。完整范围按 canonical 数据生成，不直接 `window.print()` 当前窗口
  就宣称导出了全文。
- **边界：** 私人批注／笔记默认不包含，遵循导出授权；长对话有规模限制和可见进度。
  公式、Mermaid、表格、附件占位和缺失文件需规定降级，不能宣称任意格式保真。
- **验收／价值验证：** 跨多个 Reader 窗口的合成对话逐条数量相符、不漏尾；
  中文、公式、长代码、宽表分页可读。先确认需要“打印”还是“可编辑文档”，避免做错输出。

### WEB-07 · 从搜索结果直接批量整理

- **场景／假设：** 用户搜索出一批同主题记录后，希望直接归档、移项目或导出，
  而不是记住标题，再回主列表逐条寻找。
- **现状证据：** `apps/web/features/search/search-page.tsx:40–46,88–99`
  管理的是单个键盘活动结果；批量管理位于
  `apps/web/features/conversations/conversation-list.tsx:446–536`，搜索结果未接入该流程。
- **最小版本：** 搜索页“整理这些对话”，按 conversation ID 去重并显示实际数量；
  初版只处理已加载、明确勾选的对话，复用既有确认、进度和未知结果核对。
- **边界：** 同一对话的多个命中不能重复提交；折叠的重复正文 occurrence 不等于
  用户选中了全部副本。“全部搜索结果”若未来支持，必须冻结服务器身份集与范围，
  不能把可变查询字符串直接当删除授权；既有导出限额不绕过。
- **验收／价值验证：** 多个消息命中同一对话时只执行一次；翻页或新结果出现不扩大
  已确认集合；检索条件变化保留明确的选区规则。先在小批整理任务验证节省的往返。

### WEB-08 · 两个对话的只读对照阅读

- **场景／假设：** 比较不同回答、同主题资料或导入前后记录时，用户可能需要同时
  保留两个阅读位置，而不必反复切浏览器标签。
- **现状证据：** `apps/web/app/conversations/[conversationId]/page.tsx:25–32`
  挂载单个 `ConversationReader`；现有拆分／合并是内容变换，不是双源对照。
  本次所查 Reader 入口未见选择第二个对话的对照模式。
- **最小版本：** 选择两段已授权对话，分别保留目录和真实锚点；
  首版不承诺语义对齐或自动同步滚动，小屏改为显式切换两侧。
- **边界：** 不复制第二套 canonical 状态，不因比较而切当前版本或合并正文；
  两侧导航、选择和请求相互隔离，不互相覆盖阅读位置。需单独验证双 Reader
  的事件／焦点及资源边界，不能简单把现有组件挂两次就算完成。
- **验收／价值验证：** 一侧翻页、搜索、失败和恢复不改变另一侧；退出回原锚点。
  只有实际比对任务确实比两个标签更方便时，才继续做复杂联动。

### WEB-09 · 跨对话文件目录

- **场景／假设：** 用户只记得某个 PDF、表格或图片，却不知道附在哪段对话，
  或希望按类型、大小、使用状态集中整理附件。
- **现状证据：** `apps/web/features/attachments/conversation-files-panel.tsx:69–100,145–146`
  是当前对话文件工作区；`apps/api/app/api/routes/attachments.py:252` 列表亦按对话。
  全局搜索已有附件类型，候选差异在于**无需关键词浏览与跨来源筛选**，不是再做文件搜索。
- **最小版本：** 服务端分页的个人文件目录，按项目／文件类型筛选，显示来源、
  大小和使用状态，复用现有预览及“回到原文”；首版只读。
- **边界：** 同名不等于同文件；不同所有者的相同 hash 不能暴露彼此存在。
  缺失、detached、历史引用和隔离文件不能混成普通可下载文件；
  不先遍历所有对话拉附件，也不提供未经引用检查的一键清理。
- **验收／价值验证：** 无关键词找到跨项目文件；分页与权限正确，来源定位准确。
  用实际目录规模测量后再决定是否需要索引和批量操作。

### WEB-10 · 重复对话候选审阅

- **场景／假设：** 多次导入、拆分和合并以后，用户可能想找出疑似重复记录，
  但不希望系统擅自删除带有独立批注的副本。
- **现状证据：** `apps/web/features/import/import-panel.tsx:434`
  已有相同归档提示，`apps/api/app/schemas/import_schema.py:103–108`
  有重复策略；`apps/api/app/models/conversation.py:34` 有内容 hash。
  这不等价于导入完成后的全库候选审阅。
- **最小版本：** 先做只读的严格重复候选列表，解释匹配依据，展示消息数、来源、
  项目、时间及是否有独立批注／附件；逐项打开比较。第一版不做语义近似聚类。
- **边界：** 正文 hash 相同不证明历史版本、附件、笔记或来源相同。
  不自动合并／删重；若后续提供处理，优先可逆归档且冻结明确选择。
  不能把搜索结果去重机制直接当作删除安全证明。
- **验收／价值验证：** 正文相同但批注或附件不同的合成记录必须保留差异提示；
  候选读取和比较零删除。先验证重复候选数量是否值得单建入口。

### WEB-11 · 轻量多标签，不替代项目

- **场景／假设：** 同一资料既属于某个项目，又同时涉及多个主题或处理阶段；
  用户可能需要跨项目的分类维度。
- **现状证据：** `docs/system/FEATURE_INVENTORY.md` 的“明确不包含”列出标签；
  当前管理基于 Project、置顶和归档。这是**明确扩范围候选**，不是声称现有
  项目归属只能单选，也不是认定没有文件夹树就是缺陷。
- **最小版本：** 用户手动创建／改名／删除标签，给对话添加多个标签，并可检索；
  不做层级标签、自动 AI 打标或多人共享词表。
- **边界：** 需先决定与项目的区别、同名规范、账号所有权、归档展示及
  `.cr`／离线导入导出的兼容合同。删标签不删对话；不牺牲旧包读取。
- **验收／价值验证：** 用真实分类任务判断是“跨主题标签”需求还是“保存搜索”
  已足够解决；前者未证实前不新增表和所有界面的常驻控件。

### WEB-12 · 命名导出预设与隐私清单

- **场景／假设：** 用户反复执行“交给 AI”“只留正文”“带附件归档”等不同目的的导出，
  希望复用选项，同时清楚知道哪些私人内容会包含。
- **现状证据：** `apps/web/features/exporting/export-panel.tsx:47–61,110–144`
  已有格式和附加内容开关，并通过 `stateRef` 保留面板状态；
  本次所查入口没有用户命名、选择和管理多个预设的流程。
- **最小版本：** 保存格式／附件／附加内容组合，命名、重命名、删除；
  应用后显示本次具体范围和私人内容清单，再明确开始导出。
- **边界：** 预设不保存旧 job ID、幂等键、对话 ID 或下载地址；
  不把上一份资料的批注授权继承为下一份资料的默认同意。
  私人内容默认关闭；若预设要求包含，执行前明确显示并确认。
- **验收／价值验证：** 换对话调用预设不会复用旧任务／数据；
  私人内容控制与实际制品一致。先验证用户是否确有多套重复导出配置。

### WEB-13 · 可搜索的快速操作面板

- **场景／假设：** 熟练用户知道功能名称，但不想在侧栏、更多菜单和设置中寻找；
  新用户也可能想直接搜索“导入”“下载离线”“查看书签”。
- **现状证据：** `apps/web/components/shortcut-manager.tsx:9–23`
  把 Cmd/Ctrl+K、/、Cmd/Ctrl+F 分配给搜索；已有帮助诊断，但不是动作检索。
  候选是动作发现入口，**不是把现有搜索快捷键重新命名**。
- **最小版本：** 一个可点击打开的面板，先列少量常用导航／打开操作；
  搜索动作名、展示实际快捷键和当前不可用原因，复用既有 action handler。
- **边界：** 不抢占 Cmd/Ctrl+K 的已有行为；输入法和文本编辑时不捕获字符。
  写操作仍进入原确认流程，危险动作不能被一回车直接执行；按账号／Share／Offline
  能力过滤，不能把管理员操作展示成普通可用操作。
- **验收／价值验证：** 用户能用动作名称找到入口，且面板与原菜单的权限／确认一致；
  若仅少数动作常用，优先优化原入口，不为面板本身增加一层导航。

### WEB-14 · 离线常备清单

- **场景／假设：** 用户每次出门前只想更新固定的一组项目与零散对话，
  不想下载全部，也不想重复逐项选取。
- **现状证据：** `apps/web/components/offline-sync-center.tsx:354–365`
  已支持全部、项目和单对话下载，包含附件策略与可用性计数；
  `apps/web/features/offline/library-shell.tsx:26,371–372` 使用同样的下载范围。
  本次未见命名的跨范围常备集合，因此不重复建议“增加项目下载”。
- **最小版本：** 保存一个本机、账号隔离的清单，包含目标范围及附件策略；
  用户明确点击“更新此清单”后，展示本次解析数量并复用现有增量下载队列。
- **边界：** 初版不做无上限后台自动下载、不承诺浏览器永不清缓存；
  不自动删除清单以外副本，不触碰未同步批注／草稿。项目成员变化应展示新增范围，
  去重后冻结本次请求；继续支持旧离线包和 Dexie 数据。
- **验收／价值验证：** 同一对话属于多个已选范围时不重复下载；部分失败独立恢复，
  账号切换不带入旧清单。先确认重复准备离线资料的频率，再决定是否值得持久化入口。

## 4. 推荐推进顺序

### 第一批：先验证四个用户价值明确、可依托现有能力的方向

1. **WEB-01 保存搜索：** 从已有 URL 筛选做命名入口，先不改检索引擎。
2. **WEB-04 只读版本对比：** 查看历史与修改当前版本分开，初版聚焦文字差异。
3. **WEB-02 全局书签／批注：** 先做只读聚合，不同时重构笔记和批注编辑。
4. **WEB-05 分享前预览：** 先锁定与真实 Share 相同的内容投影，再设计界面。

其中 WEB-01、WEB-04 比较适合先做有界原型；WEB-02、WEB-05 需要先确定 API
范围和权限验收。此顺序是审查建议，不代表用户已批准实施。

### 第二批：围绕明确的使用目的增强流程

- 常读长对话：WEB-03 待读；频繁按主题整理：WEB-07 搜索结果整理。
- 经常交付资料：先 WEB-12 导出预设，再确认 WEB-06 打印稿的格式需求。
- 不将四项一次性塞进首页；分别放在现有阅读、搜索和导出上下文。

### 第三批：有规模或重复需求证据后再扩展

WEB-08 对照、WEB-09 文件目录、WEB-10 重复审阅、WEB-11 标签、
WEB-13 快速操作、WEB-14 常备离线。先收集任务样例或受控使用反馈，
不要因为技术上能做就同时建设六个工作区。

## 5. 不建议借本轮顺带扩大

- **不直接上 AI 自动摘要／语义搜索／自动标签。** 当前最明确的候选可以复用既有
  canonical 数据；模型费用、隐私、错误解释和评测都需要额外证据与决策。
- **不顺带建设团队协作、评论权限和实时共编。** 这不是加一个分享按钮能完成的
  范围，需要重新设计身份、冲突、审计和数据隔离。
- **不把硬删除悄悄改成回收站。** 现有归档已经可恢复；回收站会改变释放空间、
  附件生命周期和备份语义，须单独决策，不能包装成小体验补丁。
- **不默认把“最近”重新放回桌面主导航。** 历史决定是桌面收敛、移动保留；
  若待阅读任务需要更强入口，先验证场景，不用本报告覆盖原决定。
- **不为凑功能重做已存在的同步中心、附件预览、批注筛选、任务入口或重复归档提示。**

## 6. 后续价值验证与验收原则

建议先用合成资料做四个受控任务，不收集真实正文或敏感搜索词：

| 任务 | 观察什么 | 对应候选 |
| --- | --- | --- |
| 隔天重新找到同一组资料 | 是否需要重新设置条件；是否分得清动态查询与固定清单 | WEB-01、WEB-03 |
| 找回“曾经标记过但忘记来源”的内容 | 是否能无关键词找到；是否误解失效锚点 | WEB-02 |
| 看清两版差异而不改变当前内容 | 是否误点成切换；比较是否足以支持下一步判断 | WEB-04 |
| 发出一份只含指定内容的分享 | 能否发现误包含的私人信息；预览与真实访客内容是否一致 | WEB-05 |

对其他候选，先回答三个问题：用户是否反复遇到该任务；现有路径是否已经足够；
最小版本能否不引入更大的数据与权限复杂度。没有答案就保留为候选，不制造采用率。

无论选哪项，实施前均应明确：

1. 空、加载、部分成功、失败、无权限、对象删除和账号切换的行为。
2. 持久化范围是内存、本机还是跨设备，以及退出清理和并发修改规则。
3. 私人批注、文件名、对话正文、token 与诊断日志的边界。
4. 数据量上限、分页、请求退休和未知写结果恢复，不以加载全库代替设计。
5. 对既有 Share URL、`.cr`、离线 v1/v2/v3、Dexie v2 和真实 DOM 锚点的兼容验收。
6. 有 schema 变化时保持单一 migration head；任何测试／CI／发布依后续授权执行，
   不能把本报告的验收描述写成已通过。
