# 小内存 ZIP 导入修复 — 2026-11-04

状态：源码候选，完整精确源码 CI／限内存运行／部署尚未验收。保留 `master`，
不创建新分支；后续发布必须记录新的精确 SHA，不能复用上一轮 CI 回执。

## 原因

用户报告的归档约 1.42 MiB，18 个成员，约 22 KiB 主 Markdown。
只读校验确认它不是损坏 ZIP，没有缺失附件；Markdown 有 4 个真实消息边界，
清单的 5 个消息引用仅产生警告，不能凭清单补造第 5 条消息。

生产失败在解析之前：固定 512 MiB 保留量加上传字节 × 32，合计约 557 MiB，
而当时宿主机可用约 211 MiB；640 MiB worker 的 cgroup 余量也不足。
因此失败代码是 `UPLOAD_MEMORY_PRESSURE`，不是格式不支持、缺图或 CRC 错误。
源文件保留，未提交 canonical 数据。诊断没有修改或重新提交用户数据。

## 实施边界

- 默认启用 `IMPORT_SMALL_ZIP_ENABLED`；关闭后回到原有规则。没有全局降低
  `UPLOAD_MEMORY_RESERVE_MB`，没有调整生产内存、停掉其他服务或关闭安全扫描。
- 单归档、小型单 Markdown 候选使用 **128 MiB 保留 + 64 MiB 工作集**。
  准入至少 192 MiB 有效余量，继续使用宿主机/cgroup 的最小有效读数。
  余量或 RSS 不可获取时不授予轻量资格；处理中低于 128 MiB 或 RSS 增量
  超过 64 MiB 即停止。读数不是内存预留或绝对不会 OOM 的承诺。
- EOCD 预检先于 `ZipFile` 中央目录分配；压缩／展开各 ≤32 MiB，成员 ≤256，
  中央目录 ≤256 KiB，清单／选中正文各 ≤256 KiB。不适配 ZIP64／多卷轻量路径。
- 仅一个选中正文，附件 ≤128、单附件 ≤16 MiB，草稿 ≤1 MiB、消息 ≤256、
  render blocks ≤2,048、真实资源引用 ≤1,024。专用 Conversation ZIP 内声明为
  附件的补充 Markdown 不会变成第二个对话。超预算停止，不截断正文。
- 初始分析、重新分析、分组／映射、分类、替换和提交共用策略；替换新字节
  必须重新核验，ZIP → 文本不借用旧资格。提交核对归档／派生正文／草稿哈希、
  原始源指纹、分类修订和数量。旧证明不能绕过原标准准入。
- 共享既有进程信号量，并以非阻塞 PostgreSQL transaction advisory lock
  防止 API 与 worker 同时运行已准入的解析器。锁持续到事务结束，避免持源行锁
  时等待另一事务；冲突返回可重试队列错误。SQLite 只作为本地回归替代。
- 附件有界读取、流式 staging、MIME/扫描、hash/CRC 和既有 canonical 事务保持。
  内存下降回滚会话提交并清理本次新对象，保留原上传／可重试草稿。

## 恢复与用户合同

现有 JSON 字段保存可选 `failure: {code, stage, retryable}`；会话及任务读取
投影相同安全代码，旧任务精确已知文字仍可识别。异常包装保留安全原因，
不返回路径、正文或任意异常文字。没有数据库 migration。

ImportPanel 和任务中心共用中英文错误格式：区分内存、队列、安全路径、缺失资源
和损坏归档；明确本次已停止、未导入／未提交、源文件保留，不虚称自动排队或成功。
“重试分析”使用同一 job；不要求重新上传，不创建无限自动重试。
