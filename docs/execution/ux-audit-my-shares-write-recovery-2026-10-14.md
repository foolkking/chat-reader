# UX audit — My shares revoke recovery — 2026-10-14

这是持续普通用户体验优化中的下一批本地源码修复。本批只检查设置中“我的分享”
页面的撤销操作反馈与结果核对；不改分享 API、权限、数据模型、链接语义或批量
撤销合同。不启动服务、不登录、不做浏览器或自动化验证、不提交 CI 或部署，
用户将自行验证。本记录先于源码修改建立。

## 范围与修改前证据

范围是 `apps/web/components/my-shares-panel.tsx` 中单项和批量撤销的失败反馈、
成功后的当前列表刷新与选择保留。

修改前文件 SHA-256：

`A1E569264EAF4C6DDD8F06B87C55B28D7A469812FF7ECF2838A4F19E4F33C5AB`

源码审查确认：

- `revokeShares(ids)` 抛出异常时，catch 直接把 `failure.message` 放进页面
  的 alert；网络、代理、5xx 和其他底层文本因此会暴露给普通用户。
- 撤销请求返回成功后只调用 `invalidateQueries`，没有等待当前“我的分享”查询的
  结果；撤销已经完成但后续读取失败时，用户看不到明确的“写入已确认、列表未
  刷新”状态。
- 未知撤销结果时当前选择和失败结果状态会保留，但提示没有要求先刷新核对，
  容易促使用户立即重复发起批量撤销。

## Findings

| ID | 类型／严重度／置信度 | 用户影响与处理 |

| MY-SHARE-REVOKE-ERR-01 | Defect / Medium / Observed (code)，渲染效果未验收 | 底层异常文字直接进入设置页，无法给出可执行的恢复建议。按 HTTP 状态与未知结果提供稳定双语文案。 |

## 实现边界

- 不自动重放撤销，不增加轮询，不修改 API 或服务端幂等语义。
- 未知结果时保留原选择与已有逐项结果，要求先用现有刷新按钮核对。
- 已确认的批量结果仍按现有逐项失败／重试界面展示。
- 成功撤销后只刷新当前查询；其他分享面板缓存继续失效，但不新增用户可见
  成功弹窗或打断阅读的提示。

## Planned local repair

将添加稳定的状态感知撤销错误文案；未知网络／5xx 结果明确要求刷新列表后再
决定是否重试。成功撤销后等待当前查询的读取结果，若读取失败则提示“撤销已完成，
列表刷新失败”，同时保留已生成的逐项结果和已有手动 Refresh。仅源码和文档记录
属于本批，运行时验收留给用户。

## 实施记录

`my-shares-panel.tsx` 现在将撤销写入与撤销后的列表读取分开处理：

- `ApiRequestError` 的 401、403、404、409、422、429 使用稳定的中英文恢复文案；
  网络、5xx 和未知异常不再显示底层 `Error.message`，而是说明结果尚未确认。
- 未知撤销结果保留当前选择，并要求先用现有 Refresh 核对后再决定是否重试。
- HTTP 成功返回后，当前“我的分享”查询使用已有 `refetch()` 读取一次；读取失败
  时提示撤销结果已返回但列表未刷新，避免把已完成撤销误判成失败。
- 已有逐项失败结果、批量选择、分页回收和其他分享缓存失效保持不变；没有自动
  重放、轮询或新增请求协议。
