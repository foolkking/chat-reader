# 全量离线更新失败：巨型 JSON 与客户端整包解析 — 2026-11-01

## 结论与状态

用户在 `4b4f34f` 发布后再次报告“离线包不完整或已损坏，重试将重新生成”。
2026-11-01 16:53–16:58 +08 的生产只读排查发现一个确定的容量缺陷：
最新 47 对话包的单个 `package.json` 解码后需要 **770,638,298 个 UTF-16
code unit**，超过当前 64-bit V8 的单字符串上限 **536,870,888**。
现有浏览器导入路径必须构造这个完整字符串，Chromium/V8 无法完成该路径；
若内存不足，也可能更早在整包解压阶段失败。

服务端归档 SHA-256 与数据库一致，全部 342 个 ZIP 条目的 CRC 读取通过，
UTF-8 分块解码通过；没有证据支持把这次故障归结为服务器 ZIP 损坏。
这不等于已验证全部 JSON 语义、浏览器收到的字节或浏览器实际异常栈。
截图只确定进入了 `MALFORMED` 分类，不能区分解压、字符串解码或语义校验。
本轮找到的是足以阻止完整导入的真实缺陷，而不是假称已捕获用户浏览器抛错行。

**源码修复与本机合成浏览器验收已完成，未触发 CI、未提交或部署。**
生产版本和数据保持不变。完整 CI 与部署健康通过不能替代真实数据完整更新的验收。

## 源码修复与实测容量边界

- `offline-download-plan.ts` 冻结所选范围内有变化的对话 ID，下载队列逐对话提交
  现有 v3 包任务；每个子任务保存独立幂等键、当前任务回执和已完成游标。
  不再把 47 对话合并成一个浏览器必须整体解码的 JSON 字符串。
- 每个对话仍经过原有 schema、消息计数、配额、附件和事务写入验证后才发布；
  新增预期对话 ID 校验，错误子包不能替换无关对话。单个对话原子替换，
  整批则是可恢复的逐对话提交，不宣称整批回滚。
- 新建下载复用旧失败记录、失败列表直接重试、刷新恢复旧活动任务三个入口，
  均迁移旧整包任务。旧任务可能已经获服务端受理时，按旧幂等键另存取消意图，
  不能把它错当作新子任务取消。
- 导入设置有界预算：压缩响应最多 **512 MiB**、单个 ZIP 条目最多
  **256 MiB**、全部解压条目最多 **512 MiB**。响应长度超限时不读取正文；
  没有长度头时累加实际流字节；解压前检查条目和累积量，拒绝重复条目。
  容量错误使用终止分类 `CAPACITY`，不再反复“重试重新生成”同一超限输入。
  旧副本、批注、阅读位置和待同步操作不因容量错误被删除。
- `onWriting` 状态更新现在被等待，避免已完成的子包被较晚完成的状态写入倒退。
  package v1/v2/v3、Dexie v2、既有 URL 与服务器接口均保留。

修复期间再次对现有归档作有界只读统计，47 对话 JSON 的最小／中位／p95／最大
分别为 **41,503 / 2,291,946 / 83,146,475 / 215,581,606 字节**，
其中 **2 个**超过 128 MiB。最初考虑的 128 MiB 条目预算因此被否决，而不是
把会再次阻塞真实数据的保护阈值当作修复。
当前可打包附件元数据的最大单对话总量为 **307,061,465 字节**，
最大单附件为 **52,550,582 字节**；最大 JSON 与最大附件总量的保守相加
为 **522,643,071 字节**，低于 512 MiB。附件汇总是当前只读数据库元数据，
不是从旧包逐个对话验证出的历史同一事务快照。
归档扫描使用 192 MiB 地址空间、120 秒 CPU、低优先级和 1 MiB 读取块，
耗时 50.71 秒、峰值 RSS 74,708 KiB；未下载或输出正文／业务 ID。

这些预算是明确拒绝上限，不是任意终端都不会内存不足的证明，也不是流式 JSON
导入。超过预算的未来单对话仍需分块传输／暂存协议，不能用本次补丁宣称无限容量。
真实 47 对话的生产浏览器完整更新，以及对应附件／搜索／重启阅读验收仍未完成。

## 源码因果链

1. `apps/web/lib/offline-db.ts:522–536` 顺序执行
   `response.arrayBuffer()` → `unzipSync(compressed)` →
   `JSON.parse(strFromU8(packageEntry))`。不是流式导入。
   已安装 fflate 的浏览器实现中 `strFromU8` 直接调用 `TextDecoder.decode`。
2. ZIP 与全部解压条目合计 **2,001,405,115 字节**，尚未计入字符串、
   JSON 对象、索引、缓存与写入临时对象。即使未触及字符串硬限制，
   这条路径也有显著峰值内存风险，不能用磁盘容量来证明可运行。
3. 解压异常和字符串解码／JSON 解析异常均被包装为 `MALFORMED`。
   `apps/web/lib/offline-downloads.ts` 只持久化分类，未保留安全的失败阶段。
   `apps/web/lib/offline-download-errors.ts:18` 把所有这类异常表述为包损坏。
4. 同文件的 `offlineFailureNeedsRebuild` 又将 `MALFORMED` 归为重新打包。
   同一批未变化的数据仍产生超大 JSON，所以反复点击重试不会消除容量缺陷。
5. `apps/api/app/services/offline_packages.py` 虽然每批只序列化 8 条消息，
   仍将全部对话写入同一个 `package.json`。服务端有界内存不代表客户端有界。
   当前版本、渲染块和搜索投影保留了多种必需正文表示；目录中显示的 533.9 MB
   是估计值，不是实际下载长度、JSON 大小或浏览器峰值内存。

截图中的“可离线启动 · 105 项资源”是应用壳资源状态，不证明 47 对话内容包导入成功。
这与之前恢复缺失 Context 文件、修复下载租约保护不是同一个失败阶段。
今天两次服务端打包成功说明已越过此前的生成阶段阻塞，不代表端到端问题全部解决。

- 既有 `PWA-NEG-023` 调用 `inspectOfflineBulkPutChunking(15_448)`，验证
  100 条写入分组；没有真实解压、解码和解析 895 MB JSON。
- 小包损坏、配额、事务回滚与 v1/v2/v3 兼容用例不能覆盖单字符串上限。
- 当前阅读性能／目录查询预算不是全量离线包导入容量门禁。
- 发布记录已将用户侧完整 47 对话下载列为未验收，本次实际故障将其升级为
  **已确认的客户端大包阻塞**，不应继续仅描述为“待人工检查”。

## 原始修复建议与后续边界

下面是诊断时提出的完整方向。本轮先实施了上面的自动逐对话方案与容量分类；
真正的有界 JSON 记录流、超预算单对话协议和跨格式故障矩阵仍未实现。

### 1. 不再误导用户重试

引入有限的导入阶段和容量／内存／解码错误分类；只记录大小、计数、阶段和
固定错误码，不存正文、业务 ID、路径或异常原文。大包不能处理时明确说明原因，
不要承诺“重新生成”可以修复。下载大小、解压量、存储估计必须区分。
现有旧副本、批注、阅读位置和待同步操作不能被清理。

### 2. 消除整包常驻和单字符串要求

将下载、ZIP 解压、UTF-8 解码和 JSON 读取改为有背压的有界处理；
不再对完整 `package.json` 调用一次 `TextDecoder.decode` / `JSON.parse`。
附件逐项处理，正文按有界记录处理；仅把现有代码搬到 Worker 不解决硬上限。
Worker 如有需要须使用既有静态构建／CSP 方式，不能引入 blob/eval 例外。

导入必须先暂存和完整校验，成功后才发布新副本；跨批次不能把部分新数据
标成完整包，也不能破坏旧包或待同步操作。具体暂存与原子提升方案需要在编码前
验证事务、缓存、崩溃恢复和内存上限，不能简单把一个事务拆成多次覆盖写入。
保留 v1/v2/v3 读取、Dexie v2、本机数据和既有 URL；若确需新传输格式，
应另行明确版本合同，不能偷偷改掉 v3。

按对话／容量自动分批可作过渡方案，但必须有单个超大对话兜底和明确的批次状态，
不能把“用户手动少选几条”或“取消附件”当作最终完成。

### 3. 用真实规模的合成数据补 CI

在 CI 中生成无用户内容的 47 对话／单个超大对话夹具，覆盖至少本次
895 MB JSON、超过 536,870,888 UTF-16 units 的合法输入和受限内存下的实际
浏览器导入。验证完整消息／附件／搜索计数、离线重启可读及稳定内存预算。
小尺寸注入的逻辑用例可补充，但不能代替真实大字节路径。

另覆盖 ZIP64、UTF-8 跨块、长字符串、截断、CRC／语义失败、空间不足、
取消、断网重试、崩溃及已有副本／批注保护。测试须进入实际导入路径，
不能只断言分组函数或源码字符串；不放宽原有完整性与发布门禁。
