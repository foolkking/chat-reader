# 当前对话附件上传恢复审查 — 2026-10-14

这是持续普通用户体验优化中的下一批本地源码修复。本批只检查在线 Reader
的“当前对话文件”面板；不启动服务、不登录、不做浏览器或自动化验证、不提交
CI 或部署。用户将自行验证。本记录先于应用源码修改建立。

## 范围与修改前证据

范围包括从文件选择到上传会话、逐项上传、最终加入当前对话以及列表刷新失败
时的反馈和恢复。

修改前 `apps/web/features/attachments/conversation-files-panel.tsx` 的
SHA-256：

`0CC7D41414585E0339ECF92DEC2EACEA176F46954D0A8C45C5C461C24337BA84`

源码审查确认：

- 上传异常直接使用底层 `Error.message`，可能把 API detail、传输错误或实现
  文本当作界面文案展示。
- 上传流程没有占用现有 `actionBusy`／`actionLock`；文件面板在一批上传期间
  仍可能再次发起另一批。
- 失败时只设置错误文本，不清理已有进度；旧的百分比会继续留在界面上，不能
  表示当前真实状态。
- 最终提交请求可能已经在服务端完成，但客户端在响应或随后列表刷新时失败；
  当前界面只显示普通失败，用户容易立即重复上传。服务端最终提交对同一组已
  committed item 是幂等读取，因此客户端应先核对列表，不应自动再次提交。

## 发现与决定

| ID | 类型／严重度／证据 | 用户影响与处理 |
|---|---|---|
| ATT-UPLOAD-ERR-01 | Defect / High / Observed(code) | 原始异常直接暴露，且没有稳定的下一步。改为按上传阶段提供稳定的中英文恢复提示。 |
| ATT-UPLOAD-STATE-02 | Defect / High / Observed(code) | 上传未占用批次锁，重复选择可能产生并行批次。复用现有 action lock，并让整个上传批次进入 busy 状态。 |
| ATT-UPLOAD-STATE-03 | Defect / Medium / Observed(code) | 失败后残留旧进度会误导用户。失败和成功都清空进度，保留错误状态与重新选择入口。 |
| ATT-UPLOAD-RECOVERY-04 | Defect / High / Observed(code) | 最终提交结果可能未知，直接重传有重复风险。最终提交异常后只读刷新附件列表，并明确先核对再重新选择；不自动重放写请求。 |

## 实现边界

- 只修改当前对话附件面板；不改变 API、上传协议、数据库、存储、扫描策略
  或离线附件面板。
- 不自动重试上传或最终提交，不删除用户已存在的附件。
- 不展示底层异常文本；不把“已提交但列表刷新失败”误报为上传失败。
- 只增加已有附件列表的只读刷新入口，不增加轮询、依赖或后台资源消耗。

## 实施记录

`apps/web/features/attachments/conversation-files-panel.tsx` 的上传批次现在复用
现有 `actionLock` 和 `actionBusy`，上传中不会再启动第二批；成功、失败和列表
刷新异常都会清理旧进度。上传异常不再直接展示底层异常文本，而是按创建会话、
逐项上传、最终提交和列表刷新阶段提供稳定的中英文恢复提示。

最终提交异常不会自动再次提交。界面会保留“先刷新文件列表核对，缺失项再重新
选择”的路径；所有上传错误都提供只读的“刷新文件列表”入口。没有改变上传
协议、服务端幂等语义、数据库或离线附件面板。

提交、未触发 CI 或部署。源码修改不代表运行时验收，由用户自行验证。
