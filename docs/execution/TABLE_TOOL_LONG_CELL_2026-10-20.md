## 风险与改动

此前表格行数和挂载单元格数已有上限，但单个合法单元格仍可接近整个工具
1 MiB 输入上限。即使只挂载一页，共享 Markdown/KaTeX renderer 仍可能解析
数十万字符的一个单元格。分页并未约束这个成本。

现在表格渲染预览对当前页中**超过 32,768 个 UTF-16 代码单元**的单元格使用
空展示值进入 GFM/math renderer，单元格显示省略号，并报告当前页长单元格数量。
这是 renderer 输入的展示预算，不是原文或保存限制：

- 下方 Markdown 仍完整可见、可编辑。
- 网格单元格编辑器仍载入完整值。
- 规范序列化和 Apply 使用完整草稿值，不使用展示占位。
- 未修改长单元格直接 Apply，源文逐字不变。
- 修改为短值后，提示消失且双向编辑与 Apply 正常。
- 只对当前页构造预览数据，不为长单元格优化扫描/克隆整张表。
- 可编辑预览每页最多挂载 400 个单元格（含表头）；宽表自动缩小数据行页，
  避免 200 列时一次挂载 1,200 个控制。
- 已接受的网格单元格输入只校验被修改的单元格；只有草稿已经处于无效状态时
  才退回完整表格校验。源码 Markdown 文本区仍完整解析，以确认结构和应用安全。

本次没有更改服务端、API、数据库、Markdown 合同、依赖或 canonical 内容。

证据。前后连续运行不是受控实验，也没有不同设备/CPU 节流；只作本地诊断参考：

| 合成工作负载 | 旧挂载/当前挂载 | 网格输入中位数 | Markdown 编辑中位数 | 打开耗时 |

| 200 列、248 数据行、约 499 KB | 1,200 / 400 | 130.2 → 60.4 ms | 95.2 → 35.5 ms | 417.6 → 253.6 ms |
| 10 列、4,000 数据行、约 397 KB | 310 / 310 | 92.1 → 81.9 ms | 46.3 → 31.9 ms | 271.3 → 266.6 ms |

输入样本无 long task。所有数据都是浏览器客户端值，不代表服务端 RSS、真实用户
INP、长期内存或生产 OOM。

## 明确边界与后续

- 32,768 是实现上限，不是不同硬件上的性能阈值证明；本次没有声称测得真实设备
  延迟或内存改善。
- 省略号只适用于表格富渲染预览；长单元格仍可在 Markdown 编辑区处理。
- 表格合计源大小、行列数及挂载单元格仍使用现有独立限制。
- 先前观察到的大型普通表格长任务未由此消除；仍需在真实设备/浏览器矩阵中继续
  分析，并避免以浏览器 JS heap 推断服务器 RSS/OOM。
- 不运行 CI、不推送、不部署。
