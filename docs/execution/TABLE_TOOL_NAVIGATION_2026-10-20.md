# 表格键盘导航、焦点与原生选字 — 2026-10-20

状态：持续本地优化，目标保持活动、无 Token 预算上限。不推送、不启动 CI、
不部署；无新增依赖、API、migration、导出或离线协议变化。

## 已修复的交互

- Enter/↓ 在相邻数据行间移动，Shift+Enter/↑ 反向移动；可跨越有界预览页。
  目标使用完整草稿中的行列坐标，不把当前页序号冒充真实行号。
- 四边 `+` 新增后，焦点落到新增行的首格或新增列的表头；底部新增仍显示真实末页。
- 目标尚待渲染时保留待定位请求；若用户转到 Markdown 或其他控件则放弃旧请求。
  不为了恢复焦点重挂载整张大表，也不覆盖用户的新选择。
- 末行 Enter 没有下一格时保留当前输入框，仍消费 Enter，不能提交源码表单。
- 单元格内 Shift+方向键恢复原生文本选择；Shift+Enter 仍保留上一行语义。
  不改变普通左右键在文本中移动、边界时切格、输入法组合输入及 Escape 行为。

沿用已批准的阅读工作台样式：同一张可编辑预览与下方 Markdown、现有 paper/
graphite/sea-green tokens、44px 控件和固定操作区。不加模式按钮、辅助卡片、
说明段落或新视觉 token。主要意图是让正在修表的键盘用户不丢输入位置，而不是
把表格工具扩展成完整电子表格。界面布局未改变，不宣称新的一套全界面视觉评分。

## 失败基线

1. 跨页导航首次接入时，移动到不存在的下一行仍退出输入；实际工作区的
   “table Enter cannot save”场景在 22 个先行场景通过后超时，整次失败。
   改为仅在存在目标且已接收定位时退出，修复后完整浏览器重跑通过。
2. 后续发现 Shift+↑ 被当作上一行命令，使编辑中的 input 消失并跳到表头。
   在产品修复前加强原有“native caret”场景，3 个先行场景通过后该场景失败；
   不是缺失 selector 的测试替身问题。Shift+↓ 在末行也会阻止原生选字。
   修复后实际 Chrome 同时验证两方向的原生选区与焦点，并保留边界切格检查。

## 新发现，尚未修复：围栏的容器上下文

纯源码发现器的围栏扫描虽然已消除深引用正则回溯，但对引用/列表前缀的语义
仍不完整。使用安装的 `react-markdown` + GFM 的真实 SSR 输出核对五个合成
输入，发现：

- 顶层代码围栏内的 `> ``` ` 或列表样式 `- ``` ` 不是真正的闭围栏，当前工具
  却会误关；引用内代码的更深引用样式也有同类问题，可能自动识别代码示例。
- 未闭合的引用内/列表内围栏离开容器后，外层表格已能被 GFM 渲染，但当前工具
  仍可能将其视为代码而拒绝自动识别。

这五项是明确的诊断差异，**未修复、未计为通过**。之前 500 个随机样本只是与
旧扫描语义一致，不能证明旧语义符合 GFM。另一次读取现有 CodeMirror 解析器
的有界合成试验正确区分了所检查的上下文，但不是产品实现；首个临时试验还有
脚本字符串转义错误，不属于产品失败或通过门禁。

下一步需要按真实容器上下文修正自动识别，同时避免每次操作重新构建不受控的
整篇源码 AST；明确选区仍是用户授权编辑代码示例的方式。普通大表富渲染长任务、
跨设备延迟和服务器 OOM/低内存验收也仍未解决，不能由本轮局部门禁推导为完成。
