## 2. 摘要

上一轮将继续加载、显式恢复和范围披露补到了主要入口，本轮没有证据支持整批撤销。
但“入口可用”还不能代表后续修改、排序和预览语义已经闭环。
本次收敛为 9 项有界缺陷：8 项 Medium/P2、1 项 Low/P3，其中 2 项是新增功能的
恢复／分页交互缺口，7 项是继承问题，不能全部算作本轮新回归。
优先补齐草稿丢弃失败后的意图保留，以及附件改名后的搜索和离线一致性。
随后解决分页之后的排序上限、降序重排与 TOC 续页滚动，避免“加载完即可操作”的
提示与实际行为冲突。
预览方向应从“提示截断”进一步转向“展示的数据不能错位、错名或变成内部索引”，
同时保留现有文件、解压、行列及页数预算。
这些结论形成下一轮计划，不代表授权实施，也不替代此前未提交批次的真实验证门禁。

### STATE-COMP-01 · 附件改名没有完成派生状态闭环

**证据。** `apps/api/app/api/routes/attachments.py:324–341` 只修改 `display_name`
并提交；`apps/web/features/attachments/conversation-files-panel.tsx:171–175`
也仅刷新附件列表。`services/search/search_indexer.py:191–225` 将名称写进
`search_text/title/plain_text`，`search_service.py:327–336` 从该快照返回名称；
`services/offline_packages.py:203–210,261–269` 则按 `offline_revision` 决定是否传送对话增量。
**影响。** 对已有当前消息引用且已建索引的附件改成唯一新名称后，文件面板与搜索可能
不一致；仅改名的普通离线增量更新也可能根本不传递该变化，而不只是前端缓存短暂过期。
**建议。** 在既有事务边界同步受影响搜索文档与原子 revision，再窄化刷新相关搜索／附件缓存；
复用 `services/assets/derivatives.py:151–165` 的受影响对话重建模式、
`services/conversation_revision.py:8–24` 的 revision helper 和
`apps/web/lib/reader-search-cache.ts`，不要只清缓存或全站重建。

**验收条件。** 以已有引用附件做旧名→唯一新名，检查重新查询的全局／当前对话结果与
只改名后的离线增量；保留原始文件名可检索的既有语义，不要求未被引用的上传文件突然
进入正文索引；同名 no-op 不额外推进 revision，权限／失败回滚不泄漏变化。

### FORM-COMP-01 · 删除失败后，草稿重试可能撤销用户的丢弃决定

**证据。** `annotation-workspace.tsx:160–196` 在 await 持久化前就移除队列项，
删除失败只设置错误，不保留待删除意图；`:253–260,294–299` 已先从内存删除草稿。
`:198–238` 的“重试本机草稿”随后读库，只要没有内存草稿就恢复存量记录为 `error`，
`:240–247` 的“改回已保存文本”也走同一删除路径。
**影响。** 先持久化旧草稿，再确认丢弃，若删除事务失败，用户重试后可能再次看到自己
已放弃的文字；这不是自动覆盖服务端，但会让“放弃”与“恢复”互相抵消。
**建议。** 沿用现有串行队列和 CAS，保留明确的删除意图到确认成功，重试先处理该意图再
hydrate，未确认前保留失败状态及必要的离开提醒；不承诺本机存储持续不可写时刷新仍能
永久记住丢弃，也不能为清理旧版本删除更新的草稿。

**验收条件。** 注入删除事务失败→显式重试，旧草稿不得被恢复；覆盖改回原文、重试前
重新输入、迟到删除与新版本竞争、账号／对话／模式切换。现有
`scripts/ux/annotation-comment-drafts.test.mjs:67–100` 覆盖版本与等待，
但未覆盖 workspace 中这一失败删除→hydrate 链，不能拿 helper CAS 用例替代。

### NAV-COMP-01 · “加载全部再排序”仍撞上 500 条 API 上限

**证据。** `conversation-list.tsx:72–85,163–174` 每页 100 条，
等全部加载后将可见完整 ID 序列发送；`:340,426` 提示加载全部并据此启用拖拽。
但 `apps/api/app/schemas/conversation.py:100–101` 限制 `conversation_ids`
最多 500 条，`:339` 失败提示仍是“排序未保存，请重新拖动以重试。”
**影响。** 501 条及以上加载完成后仍不能提交这条操作，照提示反复拖拽不能解决请求大小错误；
旧实现也已有该合同冲突，新分页没有将它闭环，不能算新引入的 API 回归。
**建议。** 先做明确的 500 条防护及解释，再独立选择有界的全局重排合同，
不能简单取消上限，也不能直接复用项目 `/placement`：
`services/projects/project_service.py:389–411` 写的是 `ProjectConversation.sort_order`，
而全局 `/order` 写的是 `Conversation.manual_sort_order`，两者不是同一语义。

**验收条件。** 499／500／501 条、加载未完／完成、asc／desc、归档范围、置顶与
保存失败均有确定行为；若暂只止损，必须清楚登记“大于 500 条全局拖拽暂不支持”，
不能宣称已支持任意规模排序或对已加载子集偷排。

### DATA-COMP-01 · 自定义降序拖拽后的可见顺序不能稳定保存

**证据。** `apps/web/components/sort-menu.tsx:105–117` 允许 custom 保持并切换
desc／asc；`conversation-list.tsx:163–174` 不区分方向直接发送拖拽后的序列。
`routes/conversations.py:224–225` 将序列写为递增 rank，
`:953–972` 则按 desc 读取该 rank，且置顶排序优先于 rank。
**影响。** 以三个非置顶项可见 A/B/C 为例，拖成 B/A/C 后请求写入 rank 0/1/2，
降序重新读取成为 C/A/B；这是根据读写规则推导的结果，未做运行复现。
**建议。** 区分规范存储顺序与可见方向，或明确让 custom 只提供一种固定方向；
沿用现有排序偏好和 API，不改变其他排序方式，也不能把整个置顶／非置顶分组盲目反转。

**验收条件。** 至少三个唯一 rank，升／降序分别覆盖首／中／末拖动、连续拖动及刷新，
并验证置顶边界；不能只断言请求数组变了而不核对重新读取后的可见顺序。

### NAV-COMP-02 · TOC 继续加载会再次执行活动项居中

**证据。** `features/toc/conversation-toc.tsx:41–61` 续页改变 `visibleItems`；
`:64–79` 的居中 effect 依赖 `[activeHeadingId, visibleItems]`，在 RAF 内直接写
`container.scrollTop`，`:97` 的加载更多没有区分“追加条目”与“导航到活动项”。
**影响。** 正文活动标题仍在目录首屏时，用户滚到目录底部继续加载，追加后可能又被拉回
旧活动行附近；条目虽可达，连续浏览位置却没有保住，这是新分页与旧 effect 的交互缺口。
**建议。** 将初次进入／明确活动项导航与纯追加分开，追加维持真实目录容器的滚动位置
或稳定行锚点，保留真正导航时的居中，不把该程序化滚动记录成 Reader 的用户滚动。

**验收条件。** 201／401 标题、首屏活动项、续页／失败重试保持目录浏览锚点；
主动切换活动标题或作用域仍正确定位，owner／Offline／Share 同一语义。
`scripts/ux/toc-pagination.test.mjs:19–20,71–94` 自己也注明不是浏览器滚动验收，
其“第 201 项可寻址”断言不能证明容器位置稳定。

### DATA-COMP-02 · 稀疏表格被压紧后仍展示错误的 A/B 和行号

**证据。** `complex-attachment-worker.ts:257–271` 按匹配到的 row/cell 依次 push，
没有使用行／单元格 `r` 坐标；`complex-attachment-viewer.tsx:190–192`
却按数组位置生成列名与 `rowIndex + 1` 行号。
**影响。** 合成 A1/C1 会被显示为 A/B 两列，只有第 1／5 行有值时后者会标为第 2 行；
即使没达到截断预算，用户看到的坐标也可能错误，这不是排版保真不足。
**建议。** 在现有 2,000 行／64 列预算内保留坐标，或采用带真实坐标的有界列表降级；
超远稀疏坐标不得驱动巨大数组分配，也不能删除坐标后继续伪装连续网格。

**验收条件。** A1/C1、A1/A5、显式空／自闭合单元格、超远行列坐标、普通稠密表和
Unicode 值；验证真实坐标及预算，不扩张成完整电子表格引擎。

### DATA-COMP-03 · Office 文件名顺序不能代替文档声明的内容身份

**证据。** `complex-attachment-worker.ts:112–124,251–254` 将 workbook 中的 sheet
名称与自然排序后的 `sheetN.xml` 按数组位置配对，没有解析关系目标；
`:140–147` 也只按 `slideN.xml` 文件名排序，不读取 presentation 的幻灯片顺序关系。
**影响。** 当文档声明的工作表关系顺序与文件名不一致时，名称可能配到另一张表的内容；
重排过的幻灯片也可能按内部文件名显示，而非作者声明的顺序。
**建议。** 只在已解压且受预算控制的文件集合内解析 workbook／presentation 的身份、
顺序和关系目标，缺失或无效关系明确降级；保留原预算，不联网补文件或引入全量 Office
渲染架构。

**验收条件。** 合成 sheet2→sheet1 的声明顺序、slide3→slide1 的声明顺序，
核对名称与内容／页序对应；缺失、重复、非法或外部关系目标安全降级，
并确认 32 个 sheet／500 个 slide 的限制仍有效。

### DATA-COMP-04 · 共享字符串的身份被压缩或泄漏为内部索引

**证据。** `complex-attachment-worker.ts:112–118` 用通用 `collectXmlText` 读取
shared strings；该 helper 在 `:210–217` 跳过空字符串，因此字符串表位置会变。
`:266` 又用 `shared[Number(raw)] ?? raw` 回退，索引超出 50,000 条预算时直接显示 raw。
**影响。** 空 `<si>` 在后续字符串前会使按索引读取的内容错位；索引 50,000 超出预算时，
本应是文字的单元格可能显示 `50000`，范围提示不能解释或纠正这个伪造数值。
**建议。** 为索引表保留每一个位置，包括空项；预算外或无效字符串引用显示明确占位与
范围原因，绝不冒充原始数字单元格，同时保持有界读取。

**验收条件。** 空 si／连续空项／富文本、索引 0／49,999／50,000／非法引用，
以及真实数值单元格；分别断言索引身份、明确降级和预算未放大。
`scripts/ux/complex-preview-bounds.test.mjs:38–53` 的稠密行数边界不能覆盖该问题。

### STATE-COMP-02 · ZIP 的不同资源预算被错误解释成源文件大小

**证据。** `complex-attachment-worker.ts:176–201` 对 5,000 条目、16 MiB 单项、
96 MiB 展开总量分别抛出带“预览上限”的错误；Viewer `:55–59`
一律映射为 `size-limit`，`:195–197` 统一显示
“文件超过 50 MiB 浏览器预览上限，请下载原文件。”
**影响。** 原文件很小但条目过多／展开过大的 ZIP 会得到不真实的大小解释，
用户无法判断应缩小原文件还是改用下载，虽有下载出口，但恢复信息不准确。
**建议。** 通过小型、明确的预算原因码区分源大小／条目数／单项／展开总量，
复用当前错误组件，按真实原因解释并保留下载，不调高预算或让损坏 ZIP 冒充预算限制。

**验收条件。** 51 MiB 源文件、小文件包含 5,001 项、单项超过 16 MiB、
展开超过 96 MiB、损坏 central directory 的反馈可区分；
不要只用任意“包含预览上限”字符串来判定所有错误。
