**已经有，不重新开发：** 设备登录由 Reader 授权，以该用户身份调用受限接口；保存前一次选定默认目的地。现有来源绑定会判定新建、相同、可证明的后缀追加、冲突；合成样本 3 条消息重复保存仍是同一对话，追加后是原对话 4 条，2 个文件的字节摘要和消息归属通过。分支不同时进入复核。全局/项目置顶、移动、归属文件定位和 Context 快捷导出已经存在。原验收另覆盖两用户隔离、丢失上传响应按原收据查询、已接收任务在 worker 重启与面板重载后继续。**关闭面板、重启 worker 不等于关闭并重开整个浏览器。**

## 3. 两个界面怎样改

### 原生侧栏：浏览单位只有「对话」

1. **顶栏**只放 `Chat Reader` 和有无障碍名称的设置按钮。已连接时搜索框紧随其后，提示「搜索对话…」；未连接只给 Reader 实例和「登录并连接」。账号、断开及默认保存位置放设置；首次未选目的地才显示就地选择。普通网页和 Reader 网页均可打开侧栏，不注入按钮、不读取页面。只有支持的 ChatGPT 对话显示页内保存入口。
2. **列表标题行**左「最近的对话 ▾」（可切为「已置顶」），右「所有项目 ▾」（支持未归类）；都不是新导航页。输入查询时标题改「搜索结果」，默认搜所选项目内全部可见对话，不局限于最近读过的；若显式选了仅置顶，显示可清除的条件。复用既有所有权、归档可见性和项目范围。没有命中时可清空查询或筛选，不用多张空状态卡。
3. **每条两行**：标题可点击，尾部 `…`；第二行 `项目名/未归类 · 今天/昨天/日期`，确有可靠数量才加 `📎 N`（可访问名称「N 个附件」），不列文件名。标题打开 Reader 正文；当代表性命中来自附件，行内仅提示「附件匹配」，提供去所属对话文件面板的入口。已知唯一且仍有权访问才定位具体附件，否则打开文件面板。不在插件看正文。
4. **更多菜单**放「导出上下文 .context.zip」「置顶/取消置顶」「移动到项目」「在 Reader 查看附件」（有附件才显示）。移除资料视图的「文件」标签和常驻导出按钮，不删除受权限校验的旧后端接口，文件改名等从 Reader 文件面板完成。设置、过滤、菜单各自关闭后焦点回触发点。不常驻“点击可以查看”等页脚；需要时在首次空状态说明。
5. **进行中或必须处理**只占一条紧凑状态，复核详情就地展开，不默认铺开历史。成功只留短反馈与可找回的最近结果；**警告不能只闪一下**，在相应结果/任务中保留。无任务不占位，不为此新增任务中心。

**“最近”的口径须正确。** 目前无查询走 `updated desc` 并优先置顶，不是最近打开。建议默认用 Reader 已有的 `RecentItem.last_opened_at`；未读过任何项目内容时，提供明确标注的「最近更新」列表，不把导入或更新时间写作阅读时间。已置顶视图单独取数：全部项目按全局置顶，具体项目按项目置顶；未归类用全局置顶再限未归类。查询、置顶和项目过滤在服务端分页前应用，日期使用设备本地时区；稳定排序加 ID 决胜，不从客户端一页里筛选“全部置顶”。

### ChatGPT 页：一个主按钮，不用用户盯任务

| 有什么可信证据 | 唯一主操作 | 下一步 |
|---|---|---|
| 未连接 / 首次未选目的地 | `连接 Reader` / `选择保存位置` | 在扩展或 Reader 完成，不让来源页接触 Reader 登录凭据；之后不重复确认。 |
| 可保存，尚无已证实的相同版本 | `保存到 Reader`，有明确增量可用 `保存更新` | 正常一次点击；新建目的地在扩展内可见、一处即可改。若用户明确允许在来源页显示项目名，可如图附上 `· 项目名`，否则不把私有项目名传进第三方页面。 |
| 正在采集、上传或服务端处理 | `正在保存…` | 阻止重复提交；不把“已发送”当“已保存”。详情、取消是否仍可行、长时间资源等待只在需要时显示。 |
| 当前版本已获服务端确认、内容完整 | `已存入 Reader ↗` | 点击只打开最终对话，不再上传。重访只知道“存过”而不能证明当前内容相同时，用 `打开已存版本 ↗`，次操作「检查并保存更新」。不自动读取整篇来点亮绿勾。 |
| 资源缺失 / 冲突 / 失败 | `部分已保存 ↗` / `需要确认` / `查看失败原因` | 部分完成允许打开已存正文，解释缺失与返回原页重试；分歧只可保留原件、明确另存；失败有可执行的下一步。结果未明优先查询原收据，不能用新请求盲重试。 |

目标图三种按钮是不同时间的状态，不同时展示。已生成的另一条分支、正在生成或标签已切换，都不能给当前页面贴上前一个任务的成功状态。可见的新回复可以让旧绿勾失效；反过来，消息数、时间或最后一个可见节点相同，都不足以证明内容未改。默认目标已删除/归档/失权时仅暂停新建，请用户重选，不默默落入未归类。已另存时打开**本次副本**；副本不取代原来源绑定。Reader 自身不重复注入保存按钮，正文原有 Context 入口保持。

**数据与判断边界：**

- `Attachment.conversation_id` 是非空外键；`AssetObject` 表示存储字节，Skill 成员和导出制品也不是用户自由建目录的独立文件。未找到普通用户独立文件柜的模型依据。无需为附件发明文件夹，或把文件目录原有的归档范围带到插件搜索里。
- 已有 Reader 搜索在授权范围内按对话分组。附件名、原名和**可用文本衍生件的前 256 KiB**可参与索引；索引有消息版本与附件关联条件。不是所有文件全文可搜，更不是全量 OCR。明确有限覆盖即可，不为插件建立索引、复制正文或读 Blob。附件链接以当前 Reader 所属关系为准。
- 已有服务端检查来源路径及前缀、原件当前正文/附件指纹、分享状态，并在提交时重查。Reader 端正文改动、分支分歧、无法证明的旧手动导入不得自动覆盖；**移动项目不是改正文，不能让它产生副本**。整条有效实时分享的追加仍须独立确认。不改 Markdown ZIP 格式、完整性验证、单 worker 与低内存策略。
- 现有任务恢复依靠设备账本、原上传键和服务端任务，不是无限期保存完整的本地 ZIP。已接收可重新查询；服务器未接收且临时文件已清理时，明确要求从来源重新保存。文件恢复后的再采集仍走原比较，不能承诺把文件自动补入已经保存的原件。区分“正文过大未发送”“个别附件或交互无法保留，可复核”“Reader 处理失败”；不为了给出成功提示放大内存或绕过校验。
- `.context.zip` 是**导出 Reader 已存内容到本地**，不是从 ChatGPT 保存，也不是把内容回传。默认整条对话、自动纳入适用的接续信息、附件仅元数据；显式预设才包含附件字节，包可含当前用户的批注/无冲突笔记。通用预设里的“笔记”选项不能直接当作快捷 Context 的排除保证。首次使用或修改预设时给出实际范围；下一次仍一键下载，预设失效时提示到 Reader 重选。重命名、删除、分享、批量编辑不升级为插件主操作。

## 5. 交付顺序、门禁与暂缓项

1. **A · 先做真实回执和基础保障。** 在现有分支挑出并核实前序未提交的安全/分片修正；保留不相关用户改动，不捎带本地批量选择器。双用户、无权对话、删除、归档、并发相同保存、追加期间新增实时分享均保持原门禁。新建、重复、追加数、冲突另存及“缺文件但提交成功”逐项断言实际数据库结果、项目和页面文字；旧/新客户端×旧/新能力以可选字段兼容。
2. **B · 页面按钮和原生侧栏可分开交付。** 页面联动依赖 A；列表的布局可独立进行。用同一合成夹具对照前后图：320/375/480 px、中文/英文、浅/深色、200% 缩放、超长标题及项目名。375×860 建议目标为搜索框上缘 **≤96 px**、无待处理任务时首行 **≤200 px**、有紧凑待复核时 **≤280 px**；这是待验证目标，不是已经提速的数字。目标是第一屏既能搜索又能见到对话；不靠缩字、砍警告或缩小点击区达标。检查 44 px 主要触控目标、键盘/读屏名称、Esc 返回原焦点、中文选词、焦点不因状态刷新丢失，无横向滚动。
3. **C · 做端到端回归再谈分发。** 附件名、已索引文本、同名不同对话、同一对话多命中、已删除及跨账号资料；至少 41 个对话越过默认一页，稀疏置顶跨页，核对返回 ID 唯一、项目和日期正确。去掉旧文件页后把原测试拆成“插件定位所属对话”和“Reader 原有文件操作仍受权限校验”，不以删断言换通过。正常保存一次点击；重新打开、SPA 在 A/B 来回切换、账号/实例切换、关闭面板、**彻底退出再启动浏览器**、来源或网络中断、丢成功响应、worker 重启、OPFS 空间不足、超长正文/资源超限、交互降级、部分保存、策略禁用均有独立场景。已接收只查原收据；未接收不假称可恢复；归属和用户新数据不被覆盖，临时包按任务清理。两端都下载并检查真实 Context ZIP 的成员、附件策略、当前用户笔记/批注的隔离。保留失败和跳过，最后核对实际安装的包和确切 SHA 的完整 CI；本次未提交 CI。
4. **D · 批量导入另行决策。** 尚无获准的真实官方 ZIP。请用专用测试账号，自行导出无敏感数据的小样：普通对话、项目内外、分支、图片/附件、缺项、有条件时分片。核验成员清单、路径、时间、项目稳定标识、消息/附件归属、可证明的完整性；无证据写“项目归属未验证”，不能写“未归类”或从标题猜。核实适用条款及用户实际授权；仅预览、只传选中项，验证 640 MiB 下有界处理之后再决定是否排期。在此之前不做项目/账号自动发现、全量抓取、大型面板任务中心、独立资料库或插件阅读器。

**建议审批范围：A–C；D 只收样验证。** 未知项（真实来源变更、真实官方包、实体输入设备、浏览器整进程恢复）各有独立门禁，不用合成脚本或旧版 CI 代替。

## 补充决策：更新已有对话，只能在末尾追加（2026-11-23）

**已确认的是写入规则，不是新功能已上线。** 无论从 ChatGPT 插件选择内容，还是从 Reader 网页导入文件，「更新已有对话」都只在目标对话的**当前末尾新增消息**。不提供回填原位、插到指定消息之后、重排、覆盖、删除旧消息或将来源内容设为旧消息的新版本。这不改变 Reader 原有的手动编辑工具。

| 操作 | 应看到的结果 |
|---|---|
| Reader 已有第 1–10 轮，先选来源的第 12、15 轮，另一次再选第 13 轮 | 最终是 `1–10 → 12 → 15 → 13`。同一批按来源先后，不按勾选顺序；不同批按成功追加的先后，不按来源时间重排。第 11、14 轮仍可选择。 |
| 最后一条是问题，后来才取得回答 | 回答是一条**新消息**；问题不重复、不被改写。如果目标后面已经有其他内容，即使补的是较早的回答，也只能追加在现在的末尾。 |
| 来源重新生成了旧回答，或原本缺失的附件后来可用 | 不替换旧回答、不把文件挂回旧消息。只有用户明确选作新内容才在末尾另加；文件归属新增消息。来源内容减少也不删除 Reader 的内容。 |
| 重复确认或断网后重试；从另一条来源接续 | 同一操作先查原收据；同一目标中能可靠识别的已追加项跳过。不同来源可以明确选入同一目标，不改项目或原来源绑定；无可靠来源标识的文件不靠标题或文本相似度自动认重。 |

**入口与反馈（待实现）：** 插件保留一键「保存到 Reader」，在次要菜单放「选择内容并追加到…」。Reader 对话的 `⋯ → 追加导入内容` 固定目标；普通导入仍默认新建，也可明确选已有对话。选择页支持连续或不相邻的轮次，确认按钮写「追加 X 条消息到《目标》末尾」。未选不是缺失；确认后按实际收据区分新增、已存在跳过和所选附件缺失，不自动跳走当前阅读位置。

**实现与放行条件：**

- 两个入口共用 Reader 的预览、确认和事务写入，继续分别校验网页登录或插件设备身份。服务端在提交时锁定目标，复核所有者、可写状态、到审阅时为止的目标末尾及整条实时分享；除已完成操作的无写入重试外，预览后目标或公开范围改变应重新确认。新消息的排序键必须排在已有键之后，不通过更改旧键腾位置。
- 逐条记录本次对该目标实际接收的来源身份；普通文件至少绑定本次来源制品和条目。**离散选择绝不把最大已选序号当作连续进度**，不可借此放宽现有[同源连续后缀校验](../../apps/api/app/services/extension_import.py)。网页现有[来源摘要](../../apps/api/app/services/adaptive_import/source_preview.py)只展示开头的样例，完整选择需要有界分页而非放大摘要上限。
- 用同一组合成来源分别走插件和网页：断言目标原消息 ID、顺序、正文和版本、附件归属、批注、笔记、书签与阅读位置不变；新增只出现在末尾。覆盖跳选后补选、同批重复提交、来源分支改变、同名不同源、两个客户端并发、分享状态改变、缺附件及无权限目标。现有整段追加测试不代替这些新入口的验收。

### 选择性追加时，容易做错的三个细节（设计，尚未实现）

1. **没选不等于下次自动补齐。** 举例中以后再打开来源，不能因为点了一次普通保存，就把第 11、14 轮也导进来。曾对这个来源和目标做过跳选时，提供「继续选择追加」；要补齐，由用户显式选。相同来源条目在同一目标已经存过则跳过；两个不同条目即使都写着“好的”，也不是重复。预览后目标已变，保留勾选、重新展示实际末尾再确认；若整次操作已有成功收据，则直接展示原结果。
2. **单独追加的回答不能被认成对最后一个问题的回复。** Reader [按前一条用户消息划分轮次](../../apps/api/app/services/reader_turns.py)。默认按问答轮勾选，也可只选其中一条。若该回答的原问题不是目标当前最后一轮的问题，保持回答角色和正文，在**新消息**旁标「单独追加的回答」；原问题已在同一目标且可见时才提供跳转。不要伪造提问、改写旧轮次或为说明出处带上未选正文。Reader、分享、离线和 Context 导出都要能分辨这个情形，不能只在确认框提示。
3. **只选择几条，也只传输授权的内容。** 插件先在本机选择，再传选中的正文及其勾选的关联资源；不上传其余正文、缩略图或附件。现有[完整来源包](../../apps/api/app/services/adaptive_import/reader_package.py)校验真实树路径和消息与附件的归属，不能把跳过中间节点的摘录冒充完整分支。Reader 网页若使用已有的整包上传入口，应明确：**原文件已经上传，只有选中的消息会写入目标对话**。两端共用追加规则，但不能把网页的整包上传说成仅传所选内容。

**本机现状核验（不是选择器验收）：** 用合成来源、临时 SQLite、实际 API 和 worker 执行三个场景。① 原有 3 条，追加一条正文相同但来源 ID 不同的新消息，得到 4 条；再次提交增加 0 条。旧消息、版本、渲染块、来源引用、附件及其消息版本关联逐行未变。② 两个不同后缀在同一末尾都已确认入队，先执行的追加一条，后执行的失败，目标仍为 4 条；不是两个 PostgreSQL 事务并发的证明。③ 对 5 条合成消息读取最后一条回答的完整轮次，返回第 **3、4、5** 条，而不是来源问题所在的第 1 轮，验证了单独追加回答可能被读成另一问的回复。初次探针误用只能创建一问一答的手动新建接口，第三项得到 422；改用合法导入夹具后整批 **3/3 通过**。未改产品代码、未测新的浏览器入口。

### 2026-11-24 实施前复审补充：历史保存状态漏识别

**EXT-STATE-01 · 结果反馈与导航 · Medium · Observed (code) / rendering Inferred · M**

- **位置：** Fork `reader/source-actions.js` 的 `source-state`；Reader 已提供 `POST /api/extension/v1/sources/status`。
- **证据：** 当本地 12 项任务账本中没有当前来源的已完成回执时，`source-state` 只从默认目的地返回 `save`，没有调用已有的来源绑定查询。代码另在用户手动选择「查找已存版本」时才调用 `sources/status`。因此，账本淘汰或本地状态丢失后，已保存的来源可能重新显示「保存到 Reader」；服务端重复导入仍会防止覆盖，但用户看不到现有记录的直达入口。
- **用户影响：** 用户可能再次启动一个其实已有记录的导入，再等待服务端判重；更重要的是，无法在当前 ChatGPT 对话直接打开原 Reader 对话。
- **最小建议：** 在来源仍通过当前标签页、文档和设备绑定校验后，对当前单个来源做一次有界状态查询；只把结果表达为「打开已存版本」，不宣称当前内容相同。实际选择「检查并保存当前版本」时仍走既有的正文/分支比对与安全追加规则。若接口能力缺失或查询失败，保留安全的手动查找入口，不按标题猜测。
- **验收：** 本地回执存在、无本地回执但服务端存在来源绑定、已删除/撤权目标、服务不支持能力、查询中切换标签/账号，分别确认显示与直达行为；来源状态查询不得枚举其他对话，也不得返回 Reader ID 到 ChatGPT 页面脚本。

**隐私复核（2026-11-24，代码观察）：**“每次只查一个”仍可能把用户逐次打开、但从未打算导入的对话标识发给 Reader。没有本地收据时，默认只在用户点「查找已存版本」后查询；愿意自动识别的用户可在插件设置明确开启。授权限此设备和账号，可关闭，不以已登录、有默认目标或浏览器权限代替同意。有本地收据的已保存项仍可直接打开。

**同标签换号复核（代码观察，尚不能单凭源码称作浏览器复现）：**来源页的手动查找把 `found` 留在文档里；后续刷新即使从当前 Reader 设备得到 `save`，也会在本地把它改回 `previous`。旧页面未导航时，切换设备或账号可能继续显示上一账号的「打开已存版本」。服务端所有权校验仍在，但页面向新账号作出的状态承诺可能错误。用同一真实扩展文档手动查找、保持标签和路径不变切换两套纯合成设备状态，区分“旧提示”与“实际访问成功”；不以另开标签或重新加载页面替代此场景。
