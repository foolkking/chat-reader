# 项目批量导出审查：选了多少、下载到什么、能否再导入

**结论：保留 Reader 的「批量导出所选对话」，不要把它称为「项目备份」。先修选择数和实际提交数不一致，再补整项目入口。** 从 ChatGPT Project 保存多个对话是另一个方向；当前 Reader 插件没有这个能力。本次未改变两边产品行为。

## 修复中的复审：让用户确实能核对变更

## 补查：真正选的是对话，不是项目

在本地普通账号建甲、乙、空三个项目（活动对话数 **1、1、0**）。甲乙各有一条**同名、首句也相同**的对话；甲另有一条已归档对话，账号中另有一条未归类对话。用桌面 Chromium 和 375px Edge 分别从界面操作，读取下载响应及每个 ZIP 成员，两端各用新账号重复一次，结果一致。[收据、截图与复现步骤](../evidence/project-batch-export-2026-11-23/README.md#project-objects)。

| 要解决的事 | 观察到的现状及其后果 | 判断／建议 |
|---|---|---|
| **挑中正确的同名对话** `IDENT-01` · 中 | 在「全部对话」批量勾选时，两行都叫「同名研究记录」，都没有所属项目，复选框的可访问名称也一样。四次下载都保留了两个不同条目，顺序与提交逐一一致，没有混入归档或未选对话。**不是同名覆盖，而是下载前难以辨认。** | 当列表跨项目时，在行的次要信息或选择摘要显示已有项目名，并给复选框可区分的名称；单一项目页不必每行重复同一项目。无需显示附件名称。成本 S。 |
| **把一个或多个项目带走** `FMT-02` · 用于移交时高 | 跨项目选择实际上只提交对话 ID。ZIP 是平铺的：**2 个文件、0 层项目目录、0 个项目 ID／名称**；空项目没有任何表示。分别到甲、乙项目导出，下载响应甚至建议**同一个只含日期的文件名**，尽管两份文件内容不同。没有观察到浏览器覆盖，不把同名误报为丢文件。 | 下载几条正文时继续兼容原格式。仅要打包一个项目中的对话，用「导出项目对话…」；若承诺多项目保留归属，必须显式记录项目、成员顺序和空项目，用编号或稳定标识区分而不是按标题推断。单项目下载名可含安全化的项目名；多项目用项目数／日期，**文件名不能代替清单**。格式另行演进，成本 M；含原件并可恢复另计。 |
| **归档算不算“项目全部”** `SCOPE-02` · 中 | 归档项目乙之后，它从活动项目目录消失，乙的对话仍为活动状态；已知乙的项目成员接口仍列出它。相反，甲只归档一条**对话**，甲的活动列表便不含该条。「已归档项目」的批量工具提供恢复、永久删除，未提供导出。这是两种独立状态，不宜用一个“含归档”同时解释。 | 首版在指定项目内明确「仅活动对话」；缺省不导出未归类、未选项目或已归档对话。若提供多项目选择，要另列归档项目，不能为导出而要求先恢复。内容导出遇空项目可说「没有可导出的对话」；承诺项目迁移则应保留空项目。成本 S（范围文案）／M（支持新范围）。 |

**三个入口，不做三套流程。** 项目内勾少数：`导出所选 N 条`；整个 Reader 项目：`项目 ⋯ → 导出项目对话…`，无需反复全选；多项目迁移只有在确实需要保留结构时才加，放在 Reader Web，不在插件常驻。项目导出只生成文件，不向任何已有对话写入。单对话 `.context.zip` 依然是接续上下文的次要操作。

**如果说的是从 ChatGPT 项目批量保存到 Reader：** 已打包插件不具备项目发现。建议入口叫「从导出文件批量保存到 Reader」：先在本机列出**文件能证明的来源项目**及条数，可按项目或逐条勾选；默认不选其他项目。来源不明单列（不等于项目外）；确认“来源项目 → Reader 目标项目”，不按同名认领，不自动移动已保存对话。传输按对话逐条，附件留在所属消息；缺件、冲突、失败、未开始分别反馈，已受理项用收据核对，停止只影响后续未提交项。这是建议，不是当前可用操作；未验证的真实导出文件不作为“已导入整个项目”的依据。

## 再审查：不用第二台设备，只换排序也会漏导

**已复现，非设计推测。** 在新建的 103 条活动对话项目中，分别用 1440px 和 375px Chromium，逐一核对界面勾选、独立读取的项目成员、浏览器提交、worker 结果和实际下载的 ZIP：

| 同样先勾选两条 | 点击时实际仍在项目 | 界面显示选中 | 实发 / ZIP 内对话 | 意味着什么 |
|---|---:|---:|---:|---|
| 只将标题从升序改为降序，一条落到第二页；没有人移动或删除它 | 2 | 2 | **1 / 1** | 翻出首屏不等于取消选择。这是正常单人操作也能碰到的漏导。 |
| 同账号另一请求移出一条，原页**未刷新**就导出 | 1 | 2 | **2 / 2** | 已移出的那条仍属本人，确实进了 ZIP。这符合“按明确勾选的对话导出”，不符合“导出此刻的项目”；不是跨账号访问。 |
| 移出后**刷新列表**再导出（前一次实测） | 1 | 2 | **1 / 1** | 同一选择仅因页面刷新时机不同就得到不同范围，而且两次任务都能成功。 |

**`SEL-01`（高）不是少一个提示。** 服务端旨在导出个人选中的 ID，并不接收项目 ID；前端显示的是勾选集合的数量，却从当前已加载的行重新构造提交。两端各自算对了不同的集合。建议把这两种用户意图分开：

- **`导出所选 N 条`**：勾选的身份与顺序独立于当前页；排序、翻页、加载或收起不改变集合。不必每次弹窗。确有对话移出本项目时，保留勾选，让用户选择「仍导出原选 2 条」或「只导出仍在本项目的 1 条」；已删除或失权的对话不可导出，不能静默略过。权限始终由服务端重查。
- **`项目 ⋯ → 导出项目对话…`**：无需先翻完列表。由服务端核对该账号下的项目、归档范围及有序成员，按钮写「导出《项目名》的 N 条活动对话」。若确认前换入、换出各一条，即使总数没变，也应提示名单变化。确认后的任务使用已确认的清单，不随浏览器翻页扩张，更不能补入新成员。大于现有单次限额时明确分批。**这是建议的新入口，不是现有功能。**

另有两点影响日常使用：

| 问题／证据 | 建议 |
|---|---|
| **`RETRY-01`（中，M）**：让普通合成用户的提交确实返回 `202`，只在浏览器端丢掉这次回执。原页点「导出」重试仍是 **1 个已完成任务**；刷新页面、重新勾选同一条再试则是 **2 个不同的已完成任务**。两种宽度一致。不会重复写入对话，但会重复占用单 worker、生成两份文件。 | 不笼统承诺“可安全重试”。异常态提供「核对上次导出」，仅在结果未明时保留按账号隔离的短期请求标识；可复用[对话合并已有的核对模式](../../apps/web/features/conversations/use-merge-admission.ts#L120)。原任务已受理就打开它，不再生成一份；用户主动要求重新生成另算。 |
| **`PRIV-01`（转发前，中，S）**：实际包中没有附件原件，但有原文件名、显示名；带来源的合成消息还导出了来源对话／消息标识、来源用户名和链接。额外注入的非允许来源字段没有进入来源记录。这次是本人主动下载，不是越权，也不是每条都存有这些字段。 | 将其称为「对话数据 ZIP」，不要标成“纯文本”或“已脱敏”。在导出操作附近按需说明「含正文、来源信息和附件名称；不含附件原件、批注、笔记及项目结构」。不用在主列表永久挂隐私横幅，不擅自改变兼容格式。 |

**现有入口各有用途。** 只想在本机离线读整个项目，用[离线资料库里的「下载项目」](../../apps/web/features/offline/library-shell.tsx#L931)，那不是可迁移备份。要恢复自己整个账号下的项目关系和可用原件，用[个人归档的导出、预检和新增式恢复](../system/DATA_ARCHIVE_CONTRACT.md#personal-backup-and-additive-restore)，不要为了交付一个项目而把整个账号给别人。要给下一次对话接上下文，保留单对话 `.context.zip`。若将来要**选多个项目**，应逐项目列出条数和缺件、保留各自边界；不要直接把所有对话合成一个 Context，也不要把导出当作已确认的末尾追加。

**验收顺序：** 先使显示数、请求清单和包内身份逐一相同（成员没变时不得只使数量相同），再补未确认请求核对与格式说明；整项目入口复用同一后台写包流程。现有 SQLite 17 项和新增实跑的独立 PostgreSQL 并发专项 7 项均通过，恰好说明服务端对**它收到的清单**有保障，不能替前端证明所选范围正确。见[再审查的两组真实收据和复现脚本](../evidence/project-batch-export-2026-11-23/README.md#second-pass)。以上均非生产或手机真机验收。

## 实测了什么

在本机隔离的 Reader Web、FastAPI、PostgreSQL、worker 和 Chromium 中，用普通合成用户登录。项目有 **103 条活动对话**（其中两条同名），另设归档、项目外和其他账号对话。5 条消息分别关联同一合成文件，并各有批注和笔记。分别在 **1440×900** 和 **375×900** 上从项目页操作，检查真实请求、后台任务、浏览器下载及 ZIP 的每个条目，再将原 ZIP 和解压出的一条分别交给常规导入分析。用独立于页面的同账号 API 写入模拟另一端移出对话；不是两台物理设备的实测。没有提交回导，也没用真实账号、用户文件或生产服务。

Reader 基线 `4afb430cf6d5d03b67474cd8a8d9e5ec2021935c`、Fork 基线 `a3f0ebe738a2e69ea5c866bdddb29ce119f08fc5`，均为已有 `codex/reader-extension` 的工作树。实际 Web 构建源的项目列表、项目菜单、选择栏、排序菜单、批量提交 hook 与本工作树逐文件核对，仅换行编码不同。另从 Fork 当前工作树实构插件，加载于全新浏览器配置中检查合成来源页面；未连接真实 ChatGPT 或查询其接口。

Fork 工作树中的本地选择器**不在本轮打包白名单**。单独运行其离线索引：4 条合成记录中，2 个显式项目 ID 可区分，另 2 条（含只有自定义 GPT 标识的一条）没有可证项目；重复文件被拒。原型针对解压后的 JSON，而非整份官方 ZIP；遇到含附件等不能完整处理的对话会拒绝构建；已选对象按一个 Reader 目的地发送。这些是原型边界，**不是**发布了“项目／账号全量导出”。真实官方包的分片、项目归属、分支、附件字节覆盖仍按[授权样本门槛](reader-extension-batch-sample-gate-2026-11-23.md)验证。做不到全量证明就显示“本文件可识别 N 条”，不写“账号全部”。

## 保留什么，怎样验收修复

- **已有的后台任务保留。** 实测两次下载条目按真正提交的 ID 顺序逐一匹配；包含其他账号的混合请求为 `404`。现有 17 项 SQLite 专项通过，包括同键重复提交、文件发布失败、不留半包、过期重新生成等覆盖。源码在 PostgreSQL 用同一只读快照串行写 ZIP，并在发布前复核所有权。已接收、已生成、已下载是三种状态；无需为此在侧栏另造任务中心。重新生成按当前可读数据，不是历史快照。
- **先做 `SEL-01`**：两端共同先选 2 条。另一端移出、归档或删除一条，以及只切换分页／排序四种情况，分别比对界面、请求、任务与包内数量。不得以隐式子集提交。没有变化时不多一次弹窗，网络重试不生第二个任务。
- **再做 `FMT-01`、`SCOPE-01` 和移动入口**：用 0、1、103、超 5,000 条，两个同名对话、归档、含文件／笔记及另一个用户做验收。两个方向都从 UI 到实际 ZIP 核对。若承诺项目可迁移，要从下载的原包恢复到独立目标，逐项检查项目关系、排序、附件字节及用户选择的笔记；只有正文可读不能算通过。现阶段最省事的正常用法是加载完、明确「全选」、下载；要带附件或接续上下文，用对应**单对话**入口。
- **证据边界**：375px 是桌面 Chromium 的触屏模拟，非手机真机；未测 1 GB 设备峰值、真实 ChatGPT Project、生产或完整 CI；未新建分支、发布或部署。两个浏览器宽度的详细收据、截图与复现步骤见[证据记录](../evidence/project-batch-export-2026-11-23/README.md)。
