# 补充 UX 审查：浏览器插件设备授权上限

**范围与证据。** 只审查 Reader 浏览器插件连接流程中的设备上限错误状态；不代表全产品 UX 审计。2026-11-24（Asia/Shanghai），隔离合成账户，Edge 158.0.4370.33，Reader loopback 实例。证据包括实际浏览器截图、该次 API 状态码、隔离数据库中该专用测试账户的授权数量，以及当前 Web/API 源码。没有使用真实账户或生产实例。

## 执行摘要

当一个账户达到 32 个有效插件设备授权时，服务端会以 `409` 拒绝新的授权。实际页面却显示“Not authorized. Verify this extension is registered, then reconnect from the extension.”，把设备数量限制误报成插件未登记。用户按提示反复重连也无法解除限制。Reader 已有“设置 → 账号安全 → 已授权的浏览器插件”撤销入口，但错误页面没有告诉用户应去那里处理。修复应保留未登记插件的原有提示，仅为设备上限提供准确、简短、可执行的本地化恢复说明。另需让隔离浏览器测试在每次运行前用专用账户的正式撤权接口清理旧授权，避免测试历史把正常授权流程推到上限。

## 发现

### COPY-01 · 设备授权上限被显示为插件未登记

| | |
|---|---|
| **维度** | 内容与微文案；系统反馈与恢复 |
| **严重度** | 中 |
| **置信度** | Observed（浏览器渲染、API 日志、数据库计数与源码） |
| **实施成本** | S |
| **位置** | `apps/web/features/browser-extension/consent.tsx:15–35`；`apps/api/app/services/extension_access.py:53–68` |

**证据。** 在 Edge 的实际授权页触发后，`POST /api/extension-devices/authorize` 返回 `409`；隔离库内该专用扩展 ID 有 32 条仍有效的设备授权。服务端在 `extension_access.issue_code` 中将 32 设为上限，并以 `Disconnect an older browser first.` 拒绝新授权。页面的授权处理把所有非成功响应都折叠成同一条警告：“Not authorized. Verify this extension is registered, then reconnect from the extension.” 实际页面见 [修复前截图](authorization-limit-before.png)。

**对用户的影响。** 用户会去检查插件登记或继续重连，而真正需要的是撤销一台旧设备；核心连接流程因此停住，恢复方向也不明确。

**建议。** 将 `409` 映射到简洁的中英文提示，明确去“设置 → 账号安全 → 已授权的浏览器插件”撤销不再使用的设备，然后回到当前授权页重试。保留其它状态的既有安全校验和未登记提示，不向页面输出原始服务端错误文本。

## 优先顺序

1. `COPY-01`：按 API 状态码提供设备上限的准确恢复提示；同步增加授权上限的真实浏览器回归。
2. 修复隔离测试夹具生命周期：开始测试前，通过专用合成账户的已授权设备读取/撤权接口清除上次运行留下的设备；只记录撤权数量，不输出设备 ID 或账户数据。

## 已工作且不改动

- 服务端拒绝第 33 个仍有效授权，并要求用户撤销旧设备；这是明确的保护上限，不应为让测试通过而放宽。
- 账号安全页已有可撤销的插件授权列表；这次改进只让失败状态指向已有恢复路径，不新增另一套设备管理。
- 设备授权仍须验证已登录账户、登记的扩展 ID 与短时 PKCE 授权码；错误呈现优化不改变认证条件。

## 未覆盖

- 未用生产服务器、真实用户或真实设备授权；未评估管理员修改扩展登记、网络错误和认证过期等其它失败状态。
- 隔离实验库只用于合成数据；正式生产设备列表和撤权行为没有在本次审查中操作。
