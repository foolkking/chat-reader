| 任务 | 实际判据 |
|---|---|
| 在 ChatGPT 只选几条 | 真实扩展运行在合成来源。取消时没有读取资源；在 3 条中勾选 2 条回答，ZIP 内是按来源次序排列的 2 条，包含唯一选中图片的真实字节，**没有**被排除的提问、CSV 或它们的来源关系。主「保存到 Reader」仍然执行完整保存。 |
| 另一台设备抢先追加 | 两个独立登录会话操作同一合成目标。首个确认得到 `409`，选中的 2 条仍勾选，显示另一端新增的实际末尾；显式二次确认后才落库。核对原有行身份、次序和正文；无可靠原提问的两条回答各自成轮。不把两条稀疏消息认作整条来源。 |
| 已受理，再次打开任务 | 插件路径选择了目标 A，真实 `202` 后暂停执行、刷新：仍是 A、仍是 2 条，恢复后只提交一次。网页固定目标路径从 3 条中选 2 条；排队时另一端实际写入新末尾，worker 拒绝旧请求。再刷新仍只勾原来 2 条，明确显示另一端新写入的末尾。两次刷新没有新确认请求；用户再次点击后才成功，最终只多出正确的两条。 |
| 两个写请求真的重叠 | 在隔离 PostgreSQL 中确认两笔真实事务发生锁等待，而不是用两次串行点击代替。修前，另一端已读取旧版本的手动插入会触发数据库约束异常；修后，先等同一对话的锁，再读取版本和计算顺序，明确返回业务冲突 `409`。原 2 条和先写入的 1 条保留，后写者未插入。另有 API 专项用真实追加 worker 和持有旧目标的编辑会话验证该边界。此结论针对末尾导入与手动插入，不外推到所有编辑。 |
| 从 Reader 固定目标 | 从已有对话的 `⋯` 打开「追加导入内容」，没有切换目标控件。测试上传 3 条 Markdown，选择 2 条；按源顺序追加，不插入中间。未学习的格式另测了设置格式、验证映射，再回到原追加流程；已学习的同一格式不强迫重设。 |
| 旧资料不因追加改变 | 在目标预先放入被编辑过的原消息、带版本归属的真实附件、批注、阅读书签、含引用的笔记和阅读位置。逐项比对 3 个旧消息版本、文件下载字节和挂载到哪个版本、1 处批注、1 个书签、2 个笔记块、位置的锚点及版本。分别在冲突、插件追加、网页追加后检查；主动打开阅读器造成的正常位置变更不算作追加副作用。 |
| Context 是真实文件 | 插件和 Reader 正文各下载两种 `.context.zip`。包含附件时逐一核对两个二进制文件和摘要；只导出元数据时二进制文件为 0、相关元数据为 2。每包只含本用户的合成批注和接续笔记；失效预设在两端均拒绝，不降级成范围更大的默认包。 |
| 登录竞态 | 匿名状态查询原先即使没带 Cookie，也会要求清除会话。保留先失败的测试。修后在普通 Reader 标签延迟该真实响应，在原生授权窗口实际登录后才交付；验证响应不再删除新凭据，授权可继续。无凭据访问私有 API 仍是 `401`；残留的状态标记仍清理，撤销／改密／退出原断言保留。 |
| 看得到、点得准 | 中文／英文原生侧栏、浅深色、320/375/480 CSS px 和放大状态；来源选择器与末尾争用在桌面和 375px 窄窗实测。摘要保留链接名、代码里的文本，不显示内部资源路径；把消息总数与已选数分开。手机尺寸的 Edge 是桌面窄窗，不是真机。 |

## 补充恢复审查：授权设备达到上限

2026-11-24 **06:19:54–06:24:45（北京时间）**，Edge `158.0.4370.33`，只在 `reader-scope-1123` 合成隔离实例验证。测试为设备表写入**恰好 32 条受控合成授权记录**，再通过真实授权页面和真实 `POST /api/extension-devices/authorize` 触发服务端限制；不是前端 mock。服务端确实返回 `409`，中英文页面均呈现对应的设备上限提示，并提供打开 Reader 的恢复链接。375 CSS px 下页面无水平溢出，恢复链接高 44 CSS px。截图分别为[英文](authorization-limit-after-en-375.png)和[中文](authorization-limit-after-zh-375.png)。

清除动作只按专用测试账户、已登记的扩展 ID 与确定的 fixture 哈希匹配记录，要求数量恰为 32 后才删除；清除后复查该账户设备授权为 0，随后原授权流程返回 `200`。每次运行前另外通过该合成账户已登录的 Reader API 撤销既有授权；英文轮次撤销 1 条，中文轮次为 0 条。回执只保存计数和 HTTP 状态，不保存设备 ID、凭据或授权码。代码修复将 `409` 单独映射为可恢复的中英文提示；未登记扩展及其他错误仍使用原来的通用安全提示，未放宽服务端 32 台上限。

**复现方法：**按[隔离实验说明](../../../scripts/extension-beta/README.md)准备专用 PostgreSQL、Nginx、API、单 worker、Web 和两份全新的浏览器 profile，安装绑定同一回环 origin 的实际扩展。两个浏览器串行运行 `browser.cjs` 带 `faults` 的完整路径，不使用 `-excerpt-only` 替代。对 `project-export.cjs`，见[项目范围及逐项解包](../project-batch-export-2026-11-23/README.md#implemented)。本轮浏览器走 webpack 开发服务；同源码另外跑 Web 生产构建。公开及私有正式分发、真实 ChatGPT 账号、真机、生产更新的耗时不从这些结果推导。

**保留的失败和修复：**

- 首次网关仍指向重启前的隔离 API 地址；另有授权等待超时。旧记录不算通过。后续把登录 HTTP 状态与返回授权页分开，还发现了上述被动查询清会话问题。原生身份窗口不会在所有浏览器继承测试 context 的网络路由；延迟测试因此使用另一个真实同源页面，不替授权窗口代发登录请求，不提高超时阈值。
- 取消后重开菜单曾失去正确动作；选择器检查曾把“来源 ZIP + 服务端派生 Markdown”误当多传一份，也曾直接比较重写资源链接前后的 Markdown。改为分别核实收到的逐条字节、每个成员摘要和持久化后的真实归属；并非放弃对正文或资源的校验。
- 未知 Markdown 格式曾一直显示等待，而实际上需要人确认格式。修复后沿用映射验证、禁止从该界面执行普通整包提交。375px 的首轮脚本只找桌面 `⋯` 而超时；修后必须找到**唯一可见**的真实响应式按钮，不点隐藏元素。
- 发布前对比真实 Alembic 单 head，发现发布器的兼容清单仍写 `0063`，会在签名前拒绝发布。修为 `0064`，保留对旧 `0062` 实例的正常正向迁移；跨 schema 不是程序快换，也不授予自动降库或无备份回滚。
- 修复前真实 Chrome 收到 `202`，刷新后原 2 条变成 0 条；原生 API 测试也因缺少已提交的勾选而失败。修后只从同一草稿的已受理请求取回目标、来源和勾选位置，不取回旧的同意。一次 Context 验收因测试重复登录触发 `429` 而失败；改为只复用已核实是本合成用户的会话，独立设备仍真实登录。未改服务端频率限制、超时或原断言。
- 同为 `0.2.0` 的两个实验包只有消息选择器文件不同。一次误选旧包在选择器失败。现让浏览器在启动前验证指定 ZIP 摘要、绑定地址、32 个文件的实际内容和成员集合；旧包已验证会在启动前被拒。版本号相同不能作为通过证据。
