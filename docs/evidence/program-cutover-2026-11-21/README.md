## 计时

## 功能、原始失败与发布边界

- 三组均核对未变服务的容器 ID、启动时间、PG 身份、原配置及备份集合。Web 更换时仍能提交新的对话；程序回滚后新写入可读。**只读证明**另用旧/新真实 API 完成各自写入，再用 SELECT-only 非 owner 和四个只读业务卷互读两代搜索数据。没有用 GET 方法、开发者标签或相同 Alembic head 代替证明。
- [故障与拒绝清单](checks.json)：坏签名、错 Fork、坏下载、空间不足、重复确认、协调器被终止、坏程序启动、备份被替换、完整迁移失败。后者维持隔离；已验证的程序回滚未还原旧数据。程序更新器的实验更新使用本地密钥和固定源夹具，没有冒充真实 GitHub/GHCR 发布。系统实际 systemd 开机重启未在 `king` 试验。
- 保留早期失败：夹具的构建元数据被 `umask 077` 变成应用不可读，HTTP 200 不代表新版；改为非 root 应用可读的元数据，继续要求真实构建标识。第一次并发手动对话因不满足“一问一答”返回 422，修正夹具数据而非 API。一次 `mount` 的简写在 BusyBox 上失败，显式指定源、目标后真实磁盘 scratch 启用；96 MiB 临时写入成功。Windows 原生 PATH 缺 `gzip` 的测试失败保留，补齐现有 Git 工具 PATH 后运行原断言。
- **仍然失败的发布门禁：** 带 256 KiB 有效 JSON 填充的慢速 multipart 请求在 API 收到停机信号期间完成，同一份上传的大小和 SHA 在程序回滚后仍正确。但已有 exporter 导入进入 worker 后未产生对话。原版不切换的对照和切换场景均为 `UPLOAD_MEMORY_PRESSURE`。其他故障仍执行，最后整个验收命令以 **1** 退出。没有删除“必须成功提交并在回滚后可读”的断言或调低 512 MiB 预留。
- [同一测试实例的独立额度对照及生产只读容量](disk-and-worker.json)：保持总量及 512 MiB 预留不变，相同请求在 worker **640 MiB** 限额下失败（采样最低可用约 487 MiB），临时 **768 MiB** 时实际提交成功（约 606 MiB）。实验后恢复 640 MiB；这不是对生产配置的授权或 640 MiB 门禁通过的证据。
- `king` 14:08 的只读元数据显示仍是 `v0.1.4`，独立确认现有 worker 限额 640 MiB、预留 512 MiB。备份盘可用 **3,307,960 KiB**，四业务卷已用 **4,164,604 KiB**；即使不计数据库、镜像和安全余量，仍差 **856,644 KiB**。首次引入本协议不能走快路径。不能删旧恢复点、降低备份预算或用别的实例的 CI 代替此门禁。

## 如何复测

Linux 运行 `go test ./...`（`deploy/updater`）与 `python -m unittest discover -s scripts/ci -p 'test_update*.py'`。发布的 `program-acceptance` 使用独立、受限的嵌套引擎，跑 `update-rehearsal.sh … program`；`program-benchmark.py` 写逐次 JSON，不用均值掩盖超时。随后 `update-program-negative.py` 跑同一配置的对照和故障。独立签名必须等完整 19 项资格、旧完整演练、程序演练全过。正式 SHA/运行回执与本地工作树测量是不同证据。

**完整 CI 首次运行及复测：** `00d9738425eb1bcd2a812d202c455b8f87544ea4` / `44878028709` / attempt 1，命令等待 1500.008 秒后按精确 SHA 和 job 读取。5 项失败源于在锁定摘要的测试文件追加用例；其余 10 项成功、4 项下游跳过。修复将新增测试独立登记，原九例源码及摘要完全恢复，未更改任何跳过、超时或原有守卫。新合同要求 7050 项收集、7047 项通过、三个原有允许跳过；本地实际收集 7050，新增/原管理员用例 10/10。[各项 CI 回执及修复](ci-44878028709-repair.json)。另用最终宿主机执行器独立重跑[30 次升级和回滚](repeat-browser-samples.json)：升级最慢 11.392 秒，回滚最慢 10.659 秒。重复计时未改变 640 MiB 导入门禁的失败结论。
