## Skill 管理：三个默认，个人文件继续保有

### 用户看到什么

系统默认固定三项，显示名按界面语言翻译，Bundle 本身不因语言变化复制或重写：

| 用途 | 默认 Bundle | 交付内容 |
|---|---|---|
| 接续上下文 | `context-acquisition.zip` | 外部 AI 获取上下文的能力 |
| 维护上下文 | `context-continuation-maintainer.zip` | 外部 AI 更新 Current/Index 的能力 |
| 转换格式 | `chat-transcript-normalizer-skill.zip` | 外部 AI 将不适配文本转成可导入记录的能力 |

个人设置不再有 Skill 语言切换和克隆。默认即使用系统提供的对应项；个人文件可上传、替换、下载、改名、启停、删除、设为首选，维持已确认边界。没有个人文件时，不显示一整块空上传表单。上传 MD 仍包装为同名 ZIP，保存原指令内容；不增加 Skill 查看器、在线编辑器或历史页面。

管理员只见三条系统项，下载和替换贴近名称。恢复内置作用于系统配置，不清除任何个人首选。此次问题是身份/入口残留，不能再次改写用户固定的 ZIP 来代替修复。

### 身份和旧数据怎么处理

1. 为每个 category 提供语言无关的有效系统项及首选解析；旧六个 builtin key 保留内部别名与旧 URL 兼容，不继续生成人可见的六套配置。
2. 个人 Skill 内容、revision 和旧语言元信息保留。列表可跨旧 locale 展示，不能为了列表简洁直接去重删除个人记录。
3. 增加按账户/category 的统一首选。旧账户尚无统一选择时，解析保留旧 locale 的有效首选行为；用户首次显式选择后改用统一选择，随后切换界面语言不更换文件。只有一个有效旧首选时可以无歧义迁移。两种旧首选不同的情况不按更新时间猜测覆盖。
4. 系统默认以用户指定的三份 ZIP 及管理员后来明确替换的版本为依据。旧语言记录指向相同内容时合并有效身份；内容不同时先保留原解析与历史，列出实际差异供管理员选择最终系统版本，不能借去掉语言按钮重置已替换文件。实施前检查实际数据，不能假定生产不存在差异。
5. 替换、首选、启停、删除后统一失效解析缓存；下载绑定同一 revision。个人首选不可用时显示实际回退对象。
6. 同步 API/schema、单一 migration head、旧备份恢复中的别名/选择映射和离线静态默认链接；旧客户端依然能读到兼容响应。

### 维护的一次完整操作

建议页面文案和顺序：

```text
上下文接续                         准备维护   更新文件   历史
当前要点 · Current    历史索引 · Index

尚未保存接续文件
[准备维护]   [上传已有文件]
拖入 .context.zip、current.md 或切到 Index 拖入 index.json
```

点击“准备维护”在本面板展开紧凑步骤，不叠加第二个弹窗：

1. **下载待维护的上下文包**。首次无文件时导出 Raw；已有文件时带上当前保存的文件。附件策略沿用导出能力，用户可选择。这里先导出维护输入，否则“先维护、后导出”首次使用无法开始。
2. **下载维护 Skill / 复制维护请求**。在线用个人首选或系统默认；包是交给外部 AI 的材料，网页不执行 Skill、不上传给模型。
3. **回来更新文件**。保留当前对话目标，整包/单文件拖入现有位置；保存后读到实际内容，提供“下载更新后的上下文包”。允许用户直接使用外部产物，不强迫回传。

阅读态以内容为中心；步骤只在用户点开后出现。手动编写仍保留。Current 与 Index 分别更新，最近三次历史；不重新引入候选、采用和语义校验。跨面板转换保留草稿、选项和 Reader 位置。

### 长对话提示

沿用既有提案的初始假设：**100 条非空消息或 60,000 个 Unicode 字符**达到任一项时，在“交给 AI”的导出流程内建议维护。100 条消息不是 100 个对话，也不能保证恰好 50 user + 50 assistant。字符数包含将交付的代码/工具文本，排除附件二进制；不是模型 token 上限或质量保证。

提示只展示一次紧凑行，带“准备维护”和“直接导出”，支持忽略/关闭，不弹窗、不阻断阅读。手动准备维护始终可用。已有可信基准后可考虑新增 40 条消息或 20,000 字符再提示；没有可靠覆盖信息时不根据上传时间推断“已维护到第几条”。消息修改用事实提示，不宣称语义失效。阈值属于需合成大对话与实际使用复核的产品假设，目前未实现。

## 帮助与诊断：简化表面，补齐解决路径

建议布局：

```text
使用限制                           申请调整

合并消息上限                       1,000 条

联系管理员                         写问题或求助

```

数字示例来自用户截图，不写死。删除“允许”及独立“手动诊断”区。权限判断仍在后端和相应功能入口：管理员实际关闭某功能时需要显示原因，不能因界面精简而假装功能可用。Root Admin 看到“调整系统限制”“处理用户请求”，避免向自己申请。

### 额度申请

这里明确命名为**使用限制申请**，首版仅包含单次导入大小与合并消息数，不附带储存配额、付费、自动扩容或重置周期。

用户选择一个或两个项目，看到当前值、填写期望值与原因，提交后进入本人请求详情。导入/合并超限时也可以带入该类型与所需值，但不自动提交文件名或正文。重复点击和断网重试不能新建重复请求；同类尚未处理的请求优先补充说明。

管理员在设置新增“用户请求”，可按类型/状态分页筛选，看到当前限制、请求值和说明，批准（可填写实际批准值）、拒绝并解释、回复。批准与个人限制写入同一事务；管理员看到成功后，用户能力查询、导入前检、实际上传、合并入队限制都必须一致。用户再次打开详情能看到实际生效值，不能只有邮件或成功提示。

当前代码只有实例级策略。建议新增个人增额覆盖，生效值为：

```text
导入有效值 = min(部署硬上限, max(全站默认值, 个人批准值))
合并有效值 = max(全站默认值, 个人批准值)，且不超过实现支持的硬边界
功能是否开放仍受全站功能开关控制
```

未设置个人批准值时使用全站默认。该模型只加额，不因全站以后提高默认值反而把批准过的人限制得更低。管理员可撤回个人增额，立即回到全站规则。请求、批准与撤回均留审计，使用基础 revision 防并发重复处理。

批准前必须核对 API 配置、对应上传网关和 worker 的硬边界：超出部署能力时显示需要管理员先调整部署，不允许批准一个实际传不上去的数字；不让此按钮自动改 Nginx 或部署环境。保存申请与执行导入是两件事，政策在任务生命周期变化时需明示按哪个已锁定限制接受，不在后台悄悄切换语义。

### 问题、帮助与邮件

“写问题或求助”用一个编辑面板：问题/求助类型、标题、正文；可选预览、撤销/重做、草稿保护和提交状态。复用源码编辑器的基础编辑与面板组件，不绑定消息版本服务，不把反馈写成对话正文，不自动附加当前对话或附件。

默认提交到管理员站内请求列表，使用明确的“提交给管理员”。服务端邮件可用时，另提供明确邮件通知选项；发件人用部署邮箱，收件人为服务端配置的管理员地址，不允许客户端输入任意收件人变成通用发信接口。管理员回复记录先持久化到站内，再按用户选择发送邮件通知。确认收件人可用属于部署验收，不因存在 Root 账户就假定其标识能收信。

当前 PROJECT_STATE 的已验证生产快照为 SMTP 未配置。站内申请和帮助仍应能工作；界面不能显示“邮件已发送”。投递状态单独区分“等待发送 / 已交给邮件服务器 / 发送失败 / 未启用”，邮件服务器接受也不保证进入收件箱。邮件只携带必要通知和登录后可见的详情链接，不把正文和诊断默认放进通知。

原诊断白名单可复用，但仅置于编辑器内“附上诊断信息”的未勾选项；展开可预览/复制。自动字段继续排除正文、文件名、业务标识、邮箱、Cookie、令牌与环境变量值。用户主动写入的反馈内容按私有请求保存，不写入通用审计日志。首版不增加自动读取对话或附件的反馈采集。

离线可写本机账户隔离的草稿，显示“草稿，联网后提交”；不后台自动发送。认证失效锁定草稿，原账户恢复。服务端错误保留内容；提交收到确认才标记成功。管理员只能处理有权查看的请求，用户只能访问自己的请求/回复/下载对象；账户删除、个人备份、系统备份和保留策略需要一起定义。

### 接口和持久化建议（尚未实现）

沿用当前 FastAPI、PostgreSQL、单 worker、认证/审计与限流，不引入独立客服系统。

| 接口组 | 主要动作 | 必需合同 |
|---|---|---|
| `/api/me/requests` | 创建、分页查看本人申请/问题 | UUID 来自服务端认证；幂等键、类型、允许字段、正文上限、限流 |
| `/api/me/requests/{id}`、`/messages` | 详情、补充、撤回待处理申请 | 账户隔离、基础 revision、已处理状态不可由用户改写 |
| `/api/admin/requests` | 分页、筛选、详情、回复 | Root 权限、访问与操作审计 |
| `/api/admin/requests/{id}/decision` | 批准/拒绝/关闭 | 处理结论与批准额度原子写入，幂等且校验基础 revision |
| `/api/admin/users/{id}/limit-overrides` | 查看、调整、撤回增额 | 有效值、硬边界、变更理由与审计 |
| 现有 `/api/auth/capabilities` | 返回当前账户实际生效限制 | 与导入、合并复用同一解析函数；缓存按账户隔离并更新 |
| 邮件投递任务 | 待发、有限重试、结果 | 先持久化请求，再投递；投递失败不回滚请求、不伪装已送达 |

新增请求主表、消息表、个人限制覆盖；复用已有后台任务或小型投递记录追踪邮件。无需单独建大而全工单体系。业务状态（待处理、待补充、已批准/已拒绝、已解决、已撤回）与邮件状态分开。用户可以在同一请求继续补充，避免回复与重新申请互相覆盖。

备份中个人包含本人的请求/回复，系统包含全部；个人新增恢复不能重新激活额度批准、重新发送邮件或再次发起申请，历史记录只作历史导入。管理员授权配置仅在受控系统恢复里恢复并重新检查当前硬边界。删除账户按既有任务移除私有内容并保留最小审计，不牵连其他人的对象。

## 视觉改善的具体方向

1. **一个区域一个主任务。** 下载上下文包是主按钮，Skill 下载/使用说明是次级操作。空白接续页以开始维护为主，已有内容页以阅读/编辑为主。
2. **用间距建立层级。** 导出页移除重复的输出介绍盒和内层“AI 上下文”卡，保留必要分组；系统列表把操作贴近名称。不能把所有边框都去掉，分组仍要能辨认。
3. **让内容决定留白。** 三个系统文件用紧凑行；空白页把行动和拖入区放在一起。避免大空白隔开“生成文件”和“上传文件”的关系。
4. **字号承担明确职责。** 标题、主体动作、状态/来源分三级；配额数值与单位对齐、消息数显示千位分隔。辅助文案降级，不把所有内容都做成小字来换紧凑。
5. **命名从目的开始。** 日常按钮说“维护上下文”“下载上下文包”“申请调整”，具体 Skill 名与 ZIP 后缀作为次级信息；保留 Current/Index 对专业用户的识别。
6. **触屏与键盘同等可达。** 紧凑行在窄屏换行，点击区域不随文字一起压小；Hover 辅助信息可焦点/点击打开。维护步骤、反馈编辑器有明确返回路径和焦点恢复。

这些是基于本轮截图的布局建议；未提出换品牌、渐变、玻璃卡片或大动画，因当前证据不能说明它们会改善任务成功率。

## 实施顺序与验收门槛

| 顺序 | 交付 | 关键验收 |
|---|---|---|
| 1 | Skill 身份和解析收敛，删除语言/克隆残留 | 三个系统项；个人文件/旧首选保留；界面切换不意外变更新的统一首选；管理员替换只影响系统；备份旧 key 兼容 |
| 2 | Maintainer 首次/再次维护、Acquisition/Normalizer 入口统一 | 从空白接续页走完准备→外部手动处理→回传→再导出；任意一步可退出，草稿/阅读位置不丢；实际下载是当前首选 revision |
| 3 | 请求模型、个人增额、管理员处理、反馈编辑和邮件 | 两账户隔离；提交/处理幂等；批准后真实超原限导入/合并成功；超硬限拒绝；SMTP 失败仍有请求和失败状态 |
| 4 | 帮助页与导出/设置布局整理 | 删除指定常态信息；同屏主次动作清楚；无附件/无接续时不展示误导性可选状态；错误提供恢复入口 |
| 5 | 离线、任务中心、跨入口与回归 | Maintainer 静态包缓存可用；未缓存时不提供假下载；离线不提交请求/回传；任务结果恢复对应上下文工作流 |
